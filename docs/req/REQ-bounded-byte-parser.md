## 1. Цель, область и граница доказательства

BP1 задаёт детерминированную **модель значений** в Windows PowerShell 5.1: внешний тестовый вызывающий код передаёт по одному ограниченные факты read/count/EOF/error; модель возвращает только bounded результат. Ни входной путь, FileIO, clock, Process, сеть, engine, native данные, PTT/аудио, imports engine-adapter, stdout/log или чтение окружения не входят. Проверка модели не является тестом Enforce, native byte representation, mount identity, snapshot, allocation движка, author/ownership либо транспорта. Запуск модели — отдельный будущий pure gate, не разрешён здесь. Тесты используют известные synthetic values, не события игрового движка.

Traceability: LS-08 [intent §6](<INTENT-local-radio-slice.md#L49-L60>) требует воспроизводимого evidence; LS-01/03/05–07 требуют не выдавать диагностические данные за достоверный native тракт или успешное воздействие. [RV1:28–35](<../review/R-bounded-source-reader.md#L28-L35>) выявил отсутствие нормативной основы/host и неоднозначность EOF/output. BP1-01…09 ниже относятся только к модели и не утверждают выполнение intent.

## 3. Схема событий, состояние и строгая валидация

**BP1-01 / RV1-01,02:** значение модели — неизменяемые на границе records с exact набором полей; никаких произвольных объектов, строк, путей или заранее сериализованных буферов. Все числовые поля — точный `System.Int32`, без PS coercion, boolean вместо int, decimal/string, null и массивов; флаги — точный `System.Boolean`. Проверять типы и ranges **до** арифметики, index/copy/concat. Не принимать неизвестные/отсутствующие поля. Описание значений, не код:

- `Config`: `anchor` Int32 от 1 до 262144. Константы: `C=262144` input/request bytes, `K=262144` read calls, `L=4096` content bytes/line, `W=15` lines, `O=16384` ASCII output bytes. Значения не задаются извне. Инициализация `ACTIVE` с нулевыми счётчиками, текущим номером строки 1, пустыми строкой/очередью, `pendingCR=false`, `afterTerminator=false`.
- `READ`: exact поля `kind`, `requested`, `count`, `scalar`, `error`. `kind` точное перечисление `READ`; `requested` только 1; `count` только 0 или 1; `scalar` Int32 0…255 при count=1, ровно 0 при count=0; `error` boolean. Один event — один завершённый абстрактный read, не массив; запрещены отрицательные, >1, пропуски и предварительное преобразование poison scalar. Если `error=true`, event обязан иметь `count=0, scalar=0`; после admission и обновления counters он даёт sticky `INCOMPLETE_IO` по порядку §3.1. Для реального adapter необходимо **отдельно** доказать per-call инициализацию scalar и decode до передачи; эта spec не предполагает обнуления high bits native API.
- `EOF`: exact поля `kind`, `qualified`; `kind=EOF`, `qualified` boolean. Это отдельный injected факт без read/call и без byte; `qualified=true` означает лишь, что тестовый caller модели утверждает достоверный EOF. Модель не проверяет физическую истинность; `false` → `INCOMPLETE_EOF`. `EOF` не может следовать после error/terminal или сопровождаться данными.
- `FINISH`: exact поле `kind=FINISH`, вызывается один раз после `EOF(qualified=true)`; результат terminal. FINISH раньше EOF → `INCOMPLETE_EOF`; repeated EOF, READ после EOF или нарушение схемы → `INCOMPLETE_PROTOCOL`. Любой event после terminal обрабатывается по правилу sticky terminal ниже. До FINISH ни одна queued строка не возвращается как output.

Статусы только `ACTIVE`, `EOF_SEEN`, `DONE`, `FAILED`. Любая ошибка фиксирует **первую** причину и переводит в `FAILED`; дальнейшие events не могут менять её или выдавать успех. При любом event после `DONE`, включая malformed, не анализировать payload: возвращать фиксированный bounded result `{status=FAILED, reason=INCOMPLETE_PROTOCOL, requestedBytes, successfulBytes, readCalls, totalLines}` с сохранёнными финальными counters/totalLines и пустым output. Прежний `DONE` terminal и внутреннее состояние не мутируют; ранее выданный output повторно не возвращается, переиспользование state для нового run запрещено. Пустой batch фактов сам по себе не EOF. `Config` не содержит advertised length; `GetLength==C`, совпавшие два length или отсутствие новых events не дают qualified EOF.

**BP1-02 / RV1-04:** три независимых счётчика: `requestedBytes`, `successfulBytes`, `readCalls`, начинаются с 0. До принятия READ проверять `requestedBytes+1≤C` и `readCalls+1≤K` по вычитанию либо checked Int32; при нарушении `INCOMPLETE_BUDGET`, **без** инкремента/обработки payload. После валидного запроса увеличиваются requested и calls на 1; successful увеличивается только при count=1. Обязательный инвариант `0≤successfulBytes≤requestedBytes=readCalls≤C`. `count=0,error=false` означает `INCOMPLETE_SHORT_READ`, не EOF: для модели, где `requested=1`, это ни полноценный byte, ни qualified EOF. Отрицательное/больше 1 — protocol error, error=true — IO error. Факт EOF может прийти при счётчике ровно C без запроса; иначе на C запрещено делать C+1 probe и `FINISH` без EOF приводит к `INCOMPLETE_EOF`. Никакого zero-length READ/probe или резервного extra byte; если внешний caller не может дать EOF без C+1 read, exact-cap случай остаётся incomplete. Позитивный injected EOF доказывает только модельную развязку, не native EOF.

### 3.1 Единый precedence и counters — BPV1-01 correction

Для каждого event модель MUST соблюдать ровно порядок: **(1)** terminal-state dispatch; **(2)** exact schema/type/range/coherence; **(3)** phase admission; **(4)** READ budget admission; **(5)** обновление counters; **(6)** IO/short-count; **(7)** pendingCR; **(8)** прочая encoding/content/framing; **(9)** window/output/finalization. Остановка на первой причине. Schema failure предшествует арифметике и инкрементам. Terminal `FAILED` до schema возвращает его первую failure и прежние counters/totalLines с пустым output, даже для malformed event; `DONE` до schema возвращает фиксированный misuse result §3, без повторной выдачи success.

После schema phase admission: при `EOF_SEEN` только `FINISH` допускается; второй EOF/READ → `INCOMPLETE_PROTOCOL`, без counters. В `ACTIVE` FINISH → `INCOMPLETE_EOF`; EOF(false) → `INCOMPLETE_EOF` до проверки pendingCR; EOF(true) с pendingCR → `INCOMPLETE_BARE_CR`, иначе принимает EOF и финализирует последнюю content-строку по §4. Никакой event отсутствия не создаёт failure.

Для схемно валидного READ в ACTIVE budget проверяется до обработки error: при C/C/C любой такой READ, включая coherent error=true/count0, → `INCOMPLETE_BUDGET`, counters прежние. При наличии бюджета requestedBytes и readCalls увеличиваются на 1, successfulBytes — на count, затем error=true/count0 → `INCOMPLETE_IO`, иначе count0 → `INCOMPLETE_SHORT_READ`. Только при count1 рассматривается payload: pendingCR плюс любой byte кроме LF, включая NUL/0x80 → `INCOMPLETE_BARE_CR`; без pendingCR NUL/0x80 → `INCOMPLETE_ENCODING`. Потреблённый byte уже учтён во всех трёх counters даже при последующей ошибке payload. `totalLines` меняется только на успешно завершённой строке; output при любой failure пуст.

## 4. Байты, строки, EOF и window

**BP1-03 / RV1-05:** count=1 передаёт единственный unsigned scalar 0…255. Допустимы content `0x20…0x7E` и TAB `0x09`; LF `0x0A`, CR `0x0D` — только terminators. Без pendingCR NUL `0x00`, остальные C0/DEL, byte ≥`0x80` (включая UTF-8 BOM `EF BB BF`, `0x80` и `0xFF`) дают `INCOMPLETE_ENCODING`, даже вне выбранного window; при pendingCR приоритет §3.1 даёт `INCOMPLETE_BARE_CR`. Никакой Unicode/UTF-8 нормализации, предварительного decode или замены. ASCII byte равен одному ASCII output byte и одному UTF-16 code unit, но фактические PS/.NET allocations не являются доказанным количеством байтов.

**BP1-04:** `contentLength` считает только content bytes; LF и оба байта CRLF учитываются в input budget, но **не** входят в L. До добавления символа `contentLength < 4096`; следовательно 4096 допустимо, 4097-й content byte → `INCOMPLETE_LINE_CAP` без добавления. LF завершает текущую строку (включая пустую); CR переводит в pendingCR, следующий byte обязан быть LF — иначе `INCOMPLETE_BARE_CR`, включая EOF. CR и LF могут поступать в разных events и на границе C; законченное CR без LF — failure даже при qualified EOF.

Строка нумеруется с 1 по порядку завершения. Каждый LF/CRLF завершает ровно одну строку. Empty stream = 0 строк; `LF` = одна пустая строка; `A LF` = одна строка `A`, **не** дополнительная пустая; `A LF LF` = `A`, затем пустая. EOF завершает последнюю строку только если после последнего terminator накоплено ≥1 content byte; EOF после terminator не создаёт фиктивной строки. EOF-empty и EOF после LF не меняют число строк. Принять EOF только после проверки pendingCR=false.

**BP1-05:** весь вход до qualified EOF проверяется, в том числе байты за окном. `anchor` — номер первой выбранной строки. Если totalLines < anchor, terminal `INCOMPLETE_ANCHOR` и выходных строк нет, включая empty stream. Иначе выбрать ровно `n=min(15,totalLines-anchor+1)` последовательных строк `anchor…anchor+n−1`; EOF до 15 строк **допустим** при наличии anchor и даёт n, а не ошибки/дополнения. Никакой partial success до полного scan/EOF/FINISH. Обработка строки не в window может отбрасывать content после проверки допустимых bytes/length; модель не хранит весь файл.

## 5. Output framing и память

**BP1-06 / RV1-05:** единственный успех — ASCII output: для каждой выбранной строки по порядку `L` + десятичный номер без leading zeros + `:` + исходный content + LF; в конце ровно `OK\n` (три bytes). TAB сохраняется как один byte; исходные terminators нормализуются только до одного LF output framing. Для строки номера i и длины `li`, `digits(i)=1+floor(log10(i))` для i≥1, размер строки `ri=1+digits(i)+1+li+1`; total `T=3+Σri`. Decimal digits можно считать целочисленно без float/log10. Перед любым построением строки, prefix, LF, terminal и добавлением к очереди вычислить `ri`/сумму checked арифметикой и проверить `ri≤O-currentReserved`; также заранее зарезервировать 3 bytes для `OK\n`. Если T>16384 — `INCOMPLETE_OUTPUT_CAP`, не concat, не частичная success и не обрезание. T=16384 допустимо. Все output строки содержатся только в приватной ограниченной очереди до `FINISH` после qualified EOF. Не верить injected encoded-size или считать только content; модель сама считает полные ASCII bytes.

Failure возвращает только структурированный terminal `{status=FAILED, reason=<enum>, requestedBytes, successfulBytes, readCalls, totalLines}` и пустой output; строки enum фиксированы spec, произвольный error text/exception dump не возвращается. Это **не** строка ASCII success и не часть O; отдельная bounded terminal schema — максимум 6 полей, 1 фиксированное enum из допустимых `INCOMPLETE_IO`, `INCOMPLETE_EOF`, `INCOMPLETE_PROTOCOL`, `INCOMPLETE_BUDGET`, `INCOMPLETE_SHORT_READ`, `INCOMPLETE_ENCODING`, `INCOMPLETE_BARE_CR`, `INCOMPLETE_LINE_CAP`, `INCOMPLETE_ANCHOR`, `INCOMPLETE_OUTPUT_CAP`. `DONE` terminal `{status=DONE, reason=NONE, requestedBytes, successfulBytes, readCalls, totalLines}` плюс строка output длины T≤O. Резерв 3 bytes `OK\n` принадлежит **тому же O** и не существует на failure.

**BP1-07 peak tool-owned state:** не более 1 текущей строки L=4096 ASCII code units, очереди O=16384 ASCII code units **включая prefix/LF/OK**, ≤15 descriptors `(lineNo,offset,length)`, фиксированные 3 counters + lineNo + totalLines + contentLength + outputReserved + anchor + n + state/pendingCR/flags и один input scalar. Никаких файловых/whole-stream массивов; хранить только строки внутри окна. Верхний логический content+framing inventory ≤L+O=20480 ASCII code units + 15 фиксированных descriptors + фиксированное число scalars; он **не** равен 20480 native bytes и не включает PS object/array/string headers, преобразования, временные копии или движок. Перед созданием каждой временной строки/concat допустимый implementation обязан в будущем плане перечислить **каждую живую копию** и её фактические размеры; при обычной immutable string concatenation может одновременно жить старая и новая очередь. До такого lifetime/peak proof actual heap bound — UNKNOWN, не `PASS` из логической формулы. Никакой whole-file buffering даже при file<C.

### 6.1 Mixed cases BPV1-01 — точные expected values, NOT_RUN

Во всех строках anchor=1; тройка `r/s/k` = requestedBytes/successfulBytes/readCalls; `lines` = totalLines в возвращённом result, `out=∅` — пустой output. `R(x)` — схемно валидный READ(1,1,x,false), x записан в hex (например `80` = 0x80, `41` = 0x41); `R0` — READ(1,0,0,false), `RE` — READ(1,0,0,true). Каждая строка — отдельный новый run. Для C-трасс `P` = 15 LF и 63 блока `(4096×0x41, LF)`; `P+4018×0x41` имеет ровно C bytes, 78 завершённых строк и pendingCR=false; выбранный window остаётся private.

| Trace | Точный result |
|---|---|
| `R(0D), R(80)`; отдельно `R(0D), R(00)`; отдельно `R(0D), R(41)` | FAILED/INCOMPLETE_BARE_CR, r/s/k=2/2/2, lines=0, out=∅ для каждого |
| `R(80)`; отдельно `R(00)` без pendingCR | FAILED/INCOMPLETE_ENCODING, 1/1/1, lines=0, out=∅ |
| `R(0D), EOF(true)` | FAILED/INCOMPLETE_BARE_CR, 1/1/1, lines=0, out=∅ |
| `R(0D), EOF(false)` | FAILED/INCOMPLETE_EOF, 1/1/1, lines=0, out=∅ |
| `R(0D), FINISH` без EOF | FAILED/INCOMPLETE_EOF, 1/1/1, lines=0, out=∅; до FINISH состояние было ACTIVE |
| `P+4018×41, RE` | FAILED/INCOMPLETE_BUDGET, C/C/C, lines=78, out=∅; RE не допущен и counters не увеличены |
| `P+4018×41`, затем READ(requested=1,count=−1,scalar=0,error=false) | FAILED/INCOMPLETE_PROTOCOL, C/C/C, lines=78, out=∅; schema раньше budget |
| `P+4018×41`, затем READ(1,1,0x10041,false) | FAILED/INCOMPLETE_PROTOCOL, C/C/C, lines=78, out=∅; poison не маскируется |
| Свежий `R0`; отдельно свежий `RE` | FAILED/INCOMPLETE_SHORT_READ и FAILED/INCOMPLETE_IO соответственно; оба 1/0/1, lines=0, out=∅ |
| `RE`, затем malformed event с неизвестными полями | Оба ответа FAILED/INCOMPLETE_IO, 1/0/1, lines=0, out=∅; payload после FAILED не валидируется |
| `R(41), EOF(true), FINISH`, затем READ или FINISH | Первый terminal DONE/NONE 1/1/1, lines=1, output `L1:A\nOK\n`; каждый последующий result FAILED/INCOMPLETE_PROTOCOL с теми же 1/1/1, lines=1, out=∅; исходный DONE не изменяется |
| `EOF(true), EOF(true)`; отдельно `EOF(true), R(41)` | FAILED/INCOMPLETE_PROTOCOL, 0/0/0, lines=0, out=∅; phase admission до READ budget/counters |

Для тестов F lengths относятся только к content; каждый line terminator — один LF. Для H/L допускается synthetic generator, который выдаёт bytes по одному и не сохраняет input stream как массив; тестовая нагрузка сама не расширяет model budgets. Все тройки счётчиков и output sizes в рамках Int32; API native не вызывается.

## 7. Открытые обязательства, альтернативы и handoff

**BP1-09:** неизвестны native `Read(int,1)` byte position/sign и очистка scalar, Enfusion parity, native allocations, snapshot/mount, executor/handle, log/children и policy. Они вне модели и требуют отдельных компетентных проверок; даже пройденная модель не открывает Workbench или source. Отклонён C+1 probing: он нарушал бы неизменный C input/request budget. Отклонена длина getter как замена EOF/snapshot; `ReadLine`, весь файл в массиве, подсчёт output по одному content и частичный diagnostic PASS также исключены.

**Риски:** неправильный счёт framing/состояний создаст ложное evidence; невидимая копия immutable string нарушит заявленный heap cap. Самый рискованный переход — перенос модели на native reader: его память/EOF не следуют из synthetic events. Данной фазой ничего не внедряется и rollback не нужен. Коррекция спецификации требует повторного independent review, не исправления чужих тестов ради PASS.

**Проверки статуса:** design DRAFT; независимый review/owner validation, durable record и fresh-session/явный waiver — NOT_DONE; bounded implementation plan, code writing, source review и pure gate — NOT_OPEN; compile/native-neutral/source/runtime — BLOCKED. Никакой output/audio/actuator PASS не заявляется.

**Следующая сессия:** Lead назначает независимого reviewer для проверки requirement IDs, схем, точных EOF/cap/output traces и peak copies. После принятия/записи spec и свежего перехода отдельно создаётся bounded plan с двумя точными файлами §2, чистыми тестами и распределением ответственности; затем отдельный writing GO, readback/source review и отдельный pure gate. Перед работой перечитать актуальный AGENTS, записанные ревизии intent/spec, R1/RV1 и Team решения; эта spec не разрешает native reader, процессы или действия с игрой.
