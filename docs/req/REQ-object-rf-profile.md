## Назначение и границы

**OP01.** Чистая функция выбирает назначенный RF-профиль компонента/поверхности либо проверенное правило
префаба/класса. Для ванильного и модового объекта действует один контракт. Название объекта, визуальная текстура
и BallisticInfo сами по себе не определяют радиосвойства. UNKNOWN не означает воздух, нулевые потери или LOST.

Этот срез не распознаёт объекты движка сам, не вычисляет материал/толщину стены, проёмы или потери. Он принимает
данные доверенного адаптера и проверенную конфигурацию. Реальные API, трасса входа/выхода, составные конструкции,
RF-параметры P.2040 и частотные области — последующие срезы P3. P3 целиком не закрыт.

## Вход и глобальная проверка

**OP02.** Корень — ровно `{object, profiles, prefabParents, classParents, prefabRules, classRules}`.
Ключ — как PO04: 1–64 ASCII-символа `[A-Za-z0-9_.:-]`, чувствителен к регистру. Здесь это логический ID,
а не необработанный ResourceName/путь движка; отображение фактических ресурсов на ID обязан подтвердить адаптер.
Ни trim, ни case folding, ни prefix/substring-сопоставление не допускаются.

- `profiles`: список различных ключей допустимых RF-профилей. Пустой список допустим. Это реестр ID, не каталог
  физических свойств и не доказательство применимости профиля на частоте.
- `prefabParents`, `classParents`: каждый — объект `id → parentId|null`; null означает корень. Родитель обязан
  существовать в том же графе. Самоссылки, циклы и ссылки на отсутствующего родителя запрещены во всём графе,
  включая неиспользуемые ветви. Пустой граф допустим.
- `prefabRules`, `classRules`: каждый — объект `nodeId → profileId`. Узел обязан присутствовать в своём графе,
  профиль — в profiles. Все записи проверяются до выбора, даже если есть компонент с известным профилем.

Повторяющиеся ключи JSON должен отвергнуть загрузчик до этой функции: уже разобранный dict не сохраняет такой
дефект. Native-адаптер обязан отвергнуть повторяющиеся записи до построения map. Это граница загрузчика.

**OP03.** `object` — ровно пять строк:

| Поле | Смысл |
|---|---|
| componentProfileId | явное RF-назначение компонента, ключ либо пустая строка |
| surfaceProfileId | явное RF-назначение поверхности, ключ либо пустая строка |
| prefabId | конкретный узел prefabParents, ключ либо пустая строка при отсутствии сведений |
| classId | конкретный узел classParents, ключ либо пустая строка при отсутствии сведений |
| ballisticHint | только ID подсказки баллистического материала, ключ либо пустая строка |

Непустые prefabId/classId обязаны существовать в соответствующем графе, даже при явном RF-назначении.
Пустые строки — отсутствие сведений; null, bool и числа строками не считаются. Непустое явное RF-назначение
проверяется на членство profiles только на своём выбранном уровне (OP04): неизвестное нижнее назначение
не отменяет правильное верхнее. Ошибки структуры/ключей нижнего назначения всё равно INVALID_INPUT.

**OP04. Приоритет.** После полной OP02/OP03 проверки:

1. Непустой componentProfileId: если есть в profiles — PROFILE; иначе UNRESOLVED_PROFILE, без fallback.
2. Непустой surfaceProfileId: то же.
3. От prefabId идти по родителям к корню; первое правило даёт RULE. Порядок записи map не влияет.
4. Если правил prefab нет, так же от classId по classParents; первое правило даёт RULE.
5. Если есть ballisticHint — HINT_ONLY; иначе UNKNOWN. Профиль в обоих случаях отсутствует.

Конфликт корректных уровней разрешается этим приоритетом; source и matchedKey показывают выбранное основание.
Неизвестное выбранное явное назначение не маскируется более слабым правилом или подсказкой.

## Результат

**OP05.** Неверная структура, тип, граф, правило или ключ → только `{code: INVALID_INPUT}`.
Иначе ровно `{code, knowledge, materialId, source, matchedKey}`:

| Случай | code | knowledge | materialId | source | matchedKey |
|---|---|---|---|---|---|
| известное назначение компонента | RESOLVED | PROFILE | выбранный profileId | COMPONENT | назначенный profileId |
| известное назначение поверхности | RESOLVED | PROFILE | выбранный profileId | MATERIAL | назначенный profileId |
| правило prefab | RESOLVED | RULE | выбранный profileId | PREFAB | узел первого правила |
| правило класса | RESOLVED | RULE | выбранный profileId | CLASS | узел первого правила |
| неизвестное выбранное назначение | UNRESOLVED_PROFILE | UNKNOWN | пустая строка | COMPONENT или MATERIAL | неизвестный profileId |
| только подсказка | UNCLASSIFIED | HINT_ONLY | пустая строка | HINT | ballisticHint |
| сведений нет | UNCLASSIFIED | UNKNOWN | пустая строка | NONE | пустая строка |

knowledge/materialId совместимы с PO04. Источник назначения не доказывает достоверность физических данных:
включение профиля в реестр и в production требует отдельной проверки. Никакой результат не задаёт слышимость.

**OP06.** Входы не меняются; каждый вызов возвращает новый объект только со скалярными полями.
Проверка лесов наследования завершается за конечное число узлов без рекурсивного обхода неограниченной глубины.
Производительность реального адаптера, кеширование на environmentRevision и стоимость обработки карты не измерены.

Native-вход графа сохраняет записи `{id, hasParent, parentId}` до построения map: hasParent=false означает null
родителя; hasParent=true требует непустой правильный ключ. Так parent="" (R45) не сливается с null-корнем.
Дубликаты id проверяются до построения map (Agora #3694/#3696).

## Проверка и передача

**OP07.** Нужны случаи каждого приоритета, конфликтов, ближайшего предка, модового узла, порядка записи map,
регистра и точного сопоставления; неизвестных явных назначений; пустых данных; циклов/отсутствующих родителей
в том числе неиспользуемых; ошибочных правил/типов/полей; неизменности входа и результата.
До Enforce Claude пересчитывает REQ и JSON собственным checker без чтения авторского oracle/build/test.
Неверные JSON-типы/поля явно отмечаются host-only; null-ссылки и ошибки значений проверяются также native.
