## 1. Назначение и границы

**PO01.** P2 вводит общий контракт «что лежит на пути TX→RX» для пяти семейств: рельеф, вода, постройки,
растительность, техника — и первую модель потерь — водный слой. Постройки (P3), растительность (P4) и техника (P5)
здесь получают только форму наблюдения и правила проверки, не потери. Наблюдения из мира (трассы, `GetSurfaceY`,
поверхность воды) в P2 не исполняются: эталон и native-код работают с синтетическими наблюдениями.

**PO02.** Наблюдение отделяет геометрию от знания о RF-материале. Неизвестное явно помечается `UNKNOWN` с причиной;
оно не превращается ни в воздух (0 дБ), ни в обрыв (LOST). Неполное покрытие семейства — `UNRESOLVED` для
зависящих от него слоёв, а не «препятствий нет». Решение о доставке, LinkEvaluator, S3/S3b и снимки не меняются.

## 2. Контракт наблюдения пути

**PO03. Вход `PathObservation`.**

| Поле | Домен и смысл |
|---|---|
| frequencyMHz | > 0; частота, для которой собрано наблюдение |
| environmentRevision | int 1..MAX; версия условий среды, которой соответствует наблюдение |
| tx, rx | `Endpoint` (PO05) |
| coverage | по одному значению на семейство TERRAIN, WATER, STRUCTURE, VEGETATION, VEHICLE: `COMPLETE`, `PARTIAL` или `NOT_OBSERVED` |
| segments | список ≤ 1024 записей `Segment` (PO04) |

MAX = 2147483647. **Типизация:** целые поля (environmentRevision) — int32 без перевода во float. Каждое дробное поле
(частота, координаты, глубина, startM/endM, профиль воды) сначала округляется к IEEE binary32 (round-to-nearest,
ties-to-even; overflow → ±Inf), как в S3b §1, и только затем проверяется; результат обязан быть конечным. bool и
строки не числа; лишние поля JSON запрещены.
**Длина L считается нормативно в binary32** (#3447), чтобы эталон и native одинаково решали endM ≤ L и endM = L:
d = rx.position − tx.position покомпонентно во float32; m = max(|dx|, |dy|, |dz|); при m = 0 L = 0; иначе
sx = dx/m, sy = dy/m, sz = dz/m (каждое — float32), q = f32(f32(sx·sx + sy·sy) + sz·sz) с округлением после каждого
умножения и сложения, L = f32(m · f32(√q)). L обязано быть конечным, > 0 и не больше наибольшего binary32. Дальнейшая
RF-математика — binary64 в эталоне и float32 в native.

**PO04. `Segment` — участок прямой TX→RX, занятый объектом одного семейства.**

| Поле | Домен и смысл |
|---|---|
| family | WATER, STRUCTURE, VEGETATION или VEHICLE (рельеф описывает профиль L2, PO06) |
| startM, endM | 0 ≤ startM < endM ≤ L, вдоль прямой от TX |
| entityKey | 1–64 символа из `[A-Za-z0-9_.:-]`; стабильный ключ объекта в пределах environmentRevision |
| knowledge | `PROFILE` (RF-профиль компонента или материала), `RULE` (проверенное правило префаба/класса), `HINT_ONLY` (только подсказка, например BallisticInfo), `UNKNOWN` |
| materialId | при PROFILE/RULE — 1–64 символа того же набора; при HINT_ONLY/UNKNOWN — пустая строка |
| openings | bool; известны проёмы (окно, дверь), через которые может пройти часть энергии |

Сегменты упорядочены по ключу (startM, family, entityKey) неубывающе: family сравнивается по порядку
WATER < STRUCTURE < VEGETATION < VEHICLE, entityKey — побайтно (ASCII). Пересечение сегментов **одного** entityKey
запрещено, касание (end = start) допустимо; сегменты разных объектов и семейств могут перекрываться (дерево у
стены). Составной модовый объект — несколько сегментов с одним entityKey.

**WATER-сегменты** описывают воду на заданной прямой TX→RX, в том числе у концов: [0, a], [b, L] и [0, L] (обе
антенны в одной воде). Все WATER-интервалы, независимо от entityKey, объединяются: перекрытие и касание сливаются в
один интервал, потому что при одном профиле воды стык двух водных объектов — не граница воздух–вода.
**Согласованность концов** (только при coverage.WATER = COMPLETE и известной среде обоих концов, #3449): medium конца =
WATER тогда и только тогда, когда объединённый интервал начинается в этом конце (startM = 0 для TX, endM = L для RX);
иначе `INVALID_OBSERVATION`. При неполном покрытии воды или medium UNKNOWN рассогласование не выводится — слой даёт
`WATER_COVERAGE_INCOMPLETE`.
Сравнения с 0 и L точные после binary32-типизации; в корпусе L точно представимо и в binary32, и в binary64.

**PO05. `Endpoint` — антенна одного конца.**

| Поле | Домен и смысл |
|---|---|
| position | вектор (м), мировая система |
| medium | `AIR`, `WATER` или `UNKNOWN` |
| depthM | при WATER: ≥ 0, глубина антенны под локальной поверхностью воды (факт наблюдения; в потерях v0.3 не участвует); при AIR и UNKNOWN — 0 |

Тип водоёма (морская, пресная, конкретное озеро) не входит в наблюдение (#3415).

**PO06.** Рельеф описывается существующим профилем L2/S1 и в сегменты не входит, чтобы не учитывать его дважды.
coverage.TERRAIN фиксирует, получен ли профиль.

**PO07. Проверка наблюдения.** Результат — `VALID` или `INVALID_OBSERVATION` (структура, тип, домен, L, порядок,
перекрытие одного объекта, materialId вопреки knowledge, рассогласование medium конца и водных интервалов, поля
Endpoint вопреки medium).
Проверка глобальная: дефект последней записи делает наблюдение недействительным целиком.

**PO08. Источники движка (DOC_ONLY, в P2 не исполняются).** Высоты — `GetSurfaceY` (S1). Вода —
`ChimeraWorldUtils.TryGetWaterSurface(world, point, out surfacePoint, out EWaterSurfaceType, …)` и
`TryGetWaterSurfaceSimple` (Script API Public, установленная документация); значения `EWaterSurfaceType` в документации
не перечислены и в P2 не используются. Постройки и техника — трассы мира и тип сущности; материал —
`GameMaterial`/`BallisticInfo` только как подсказка (`E-workbench-source.md:240–252`).

## 3. Водный слой `water_p527`

**WL01. Среда.** Комплексная относительная проницаемость εw = ε′ − jε″ по P.527-6 §5.1.2, ур. (14)–(27), от частоты
f (ГГц), температуры T (°C) и солёности S (‰). Две частоты Дебая f1s, f2s и параметры εss, ε1s, ε∞s — ур. (17)–(21)
на основе ур. (8)–(13); в ε″ входит член проводимости 18·σsw/f (ур. 16), σsw = σ35·R15·RT15, RT15 = 1 + α0·(T−15)/(α1+T)
(ур. 22–27). Проводимость входит только в ε″ и второй раз не добавляется (#3410). S = 0 — чистая вода (ур. 5–7).
Область: −4 ≤ T ≤ 40 °C, 0 ≤ S ≤ 40 ‰ (§5.1), f ≤ 1000 ГГц (Annex 1).

**WL02. Профиль воды — один на мир** (#3415): `{tempC, salinityPpt}` — усреднённые свойства водоёмов карты.
Это `ASSUMED_CONFIG`: значения задаёт владелец или калибровка, производственных чисел по умолчанию нет; в корпусе —
TEST_ONLY. Сырые дБ/м в конфиг не выносятся: затухание воды меняется с частотой на порядки, а одно ядро служит и
радио, и сотовой связи.

**WL03. Затухание.** n = √εw — главный корень, Im n ≤ 0. Погонные потери мощности
αdB = 20·log10(e)·(2π/λ)·|Im n| дБ/м, λ = c/f, c = 299 792 458 м/с. Это то же, что 20·log10(e)/δ, где δ — глубина
проникновения по амплитуде, P.527-6 ур. (4).

**WL04. Граница воздух–вода.** Нормальное падение: коэффициент прохождения мощности T = 1 − |Γ|² = 4·Re(n)/|1 + n|²
(Γ = (1 − n)/(1 + n); вторая форма без вычитания близких чисел, #3448), Lint = −10·log10 T дБ на один переход.
Это оценка, не строгая нижняя граница: при наклонном падении TM-волны около псевдо-угла Брюстера отражение бывает
меньше. Поэтому водный слой v0.3 **не** выдаёт строгих границ для P1 (P1 получает MISSING_PATH_BOUND).

**WL05. Только заданный путь.** Слой оценивает воду на той прямой TX→RX, которую описывают сегменты; геометрию
пути он не меняет и маршрутов не выбирает. Lwater = Σ длин объединённых WATER-интервалов · αdB; переходы
воздух–вода — внешние концы объединённых интервалов: +1 за startM > 0, +1 за endM < L; потери L = Lwater + число
переходов · Lint.

**WL06. Открыто (следующий срез).** Для погружённой антенны прямая TX→RX при малом угле места проходит в воде намного
длиннее, чем преломлённый луч, почти нормальный к поверхности. Такой путь — **отдельная геометрическая кандидатура** со
своими воздушными наблюдениями (рельеф, постройки, растительность заново), а не подмена длины внутри этого слоя
(#3431, #3433). Оценку его длины в поглощающей воде нельзя брать по |n|: контрпример codex
#3434/#3435 для TE-волны при одной плоской границе показал, что такая граница не держит. Метод — задача этого среза.
До него слой честно считает заданный путь.

**WL07. Результат.** Порядок причин: `INVALID_OBSERVATION` (PO07) → `INVALID_PROFILE` (профиль — объект ровно с
tempC и salinityPpt, числа по PO03) → `WATER_COVERAGE_INCOMPLETE` (coverage.WATER ≠ COMPLETE либо medium UNKNOWN у
любого конца) → `NO_WATER` (нет WATER-интервалов: слой 0 дБ — вычислено, не absent) →
`OUT_OF_MODEL_DOMAIN` (T или S вне §5.1, f > 1000 ГГц) → `NUMERIC_FAILURE` (ε′, ε″ или |εw| не представимы конечным
binary32 (#3448), либо любое выходное число неконечно, отрицательно или больше наибольшего binary32) → `OK`. Значение слоя `lossDb` ≥ 0 есть только при OK и NO_WATER;
иначе слой absent и причина для UNRESOLVED. При OK выдаются также αdB, Lint, объединённые интервалы, суммарная
длина воды и число переходов. Водный слой никогда не
объявляет LOST сам: это решают отсечка P1 и evaluator.

## 4. Проверка и передача партнёру

**PO09.** Эталон `oracle/path_observation_oracle.py`, корпус `oracle/vectors/path_observation_v1.json`, сборщик
`oracle/build_path_observation_vectors.py` (ожидания — из эталона). Проверяются все отказы PO07, порядок семейств,
перекрытие и касание одного объекта, согласованность концов, binary32-типизация, водный слой (вода у одного и у обоих
концов, [0, L], отрезки посреди пути, объединение перекрытия и касания разных объектов, граница области T/S,
неполное покрытие, переполнение).
Unit-тесты сверяют ε с P.527-6 Fig. 2 (T = 20 °C) и глубину проникновения с Fig. 1, σsw 35 ‰ при 20 °C ≈ 4.79 См/м,
и тождество αdB = 20·lg(e)/δ. Native сравнивает коды строго, числа — с допуском max(1e-3 дБ, 1e-5·|x|).

Корпус v1 (заморожен): 51 случай (O01–O24 без O22 — наблюдение, W01–W28 — водный слой), LF SHA-256 `7a12ed92587318108059a213ace1d3f4286ad9a66bf86e8eb63dd4cdc7eea032`.
Ошибки JSON-типа O16 (лишнее поле) и O19 (bool вместо числа) недостижимы в типизированном Enforce и остаются host-only;
остальные 49 — для native. Команды: `python oracle/path_observation_oracle.py --check oracle/vectors/path_observation_v1.json`;
`python -m unittest discover -s oracle -p test_path_observation_oracle.py`.
