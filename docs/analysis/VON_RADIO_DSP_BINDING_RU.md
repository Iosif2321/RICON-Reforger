## Доказанный runtime provider contract

Обозначение `T` ниже — private AudioSourceTemplate из VonStream+20; `R=T[+28]` — связанный AudioProjectRes. Оба типа опираются на exact constructor RTTI; типы C-параметров не используются как ABI-доказательство.

1. **Вход reader.** A1AB70 принимает T вRCX и connection descriptor вRDX. Читает signed16 selector `[RDX]` и при неотрицательном значении signed16 output port `[RDX+2]`. Проверяет signal index против `[T+24]`; вне диапазона возвращает0. В допустимой ветви берёт signal object `S=R[+148][signalIndex]`.
2. **Контекст graph hydration.** A1ABAB..A1ABEE собирает четыре qword значения: `[&S,&R,T,&signalIndex]`. A1ABF3 вызывает A17BB0 на `S+90` и этом контексте. A1ABF8..A1AC02 затем вызывает E9DF70 с `RCX=T+10`, `EDX=outputPort`, `R8D=signalIndex`. Итак, control читает runtime signal state конкретного T; у разных native sender streams сохраняется собственный T. Это не доказывает источник arbitrary Input внутри этого state.
3. **Hydration contributions.** A17BB0 обходит0x40-byte records в `S+90`, сопоставляет record ID с массивом S+60/count+6C и получает двухчастный resolved item через A1A950. Если item ID=-1 либо port<0, вклад пропускается. E9D6C0 возвращает kind; тело допускает только9 и0x1A. Это ветви resource items, не объявленные здесь entity component kinds.
4. **Kind9 = ProjectSignal.** На A17C89/A17C95 передаются точные TD `1420CD8F0 = ProjectSignal@enf` и `1420CD8C0 = AudioProjectItem@enf`. После resource item lookup/cast получает signal index через A17DB0 на `R+48`. На A17CC2..A17CD8 читает через virtual slot+8 у subobject `T+10`, передавая resolved output port и полученный signal index. Значение возвращается вXMM0. Known constructor vtable141A045E0 наT+10 даёт для этого slot target **140A1AC90**. Его body не исследовался в этой задаче.
5. **Kind0x1A = ProjectVariable.** На A17D04/A17D10 TD `1420CD918 = ProjectVariable@enf` и baseAudioProjectItem; A17D26..A17D34 вызывает virtual slot+20 первичного T с полученным variable item. Known primary vtable141A045B0 даёт target **140A1ADE0**. Его body также не исследовался. Наличие этой ветви не означает script set/get local audio variables и не превращает ProjectVariable в SignalsManager signal.
6. **Применение полученного float.** A17D37..A17D59 пишет XMM0 в три floats соответствующей0x10-byte S state entry и устанавливает entry+0C=1. A17D5E..A17D6F передаёт этот же floatXMM3, record ID и signal index в E9DFE0 наT+10 с byte flag1. Следовательно, hydration реально подаёт значение в compiled runtime graph, а не просто ищет metadata.
7. **Другие reader selectors.** -2 прямо возвращает float descriptor+4. -4 берёт resource item изR+88, получает provider вызовом DFE5F0 с mode byteT+90 и tail-jumps E11CF0. -8 берёт provider изT+80, тот же item array R+88 и tail-jumps E11CF0. Остальные отрицательные значения возвращают0. Содержимое E11CF0/DFE5F0 и семантический типT+80 в этом probe не установлены; из их наличия не выводится sender binding.

## Что остаётся открытым после лимита трёх функций

Новая доказанная цепочка — **radio GainEvaluate → AudioSourceTemplate reader → typed ProjectSignal/ProjectVariable hydration → собственный IOP runtime state**. До неё уже был доказан native hardcoded receive-q setter в том же private state. Это объясняет, где встречаются числовой q и DSP control, но не показывает универсальный автоматический копировщик всех sender signals.

Чтобы заявить положительный custom Input bridge, нужно ещё доказать, что имя arbitrary source signal разрешается к manager конкретного sender proxy на конкретном listener и его актуальной generation. Экспортированные bodies не устанавливают эту связь. A19930 передаёт инициализацию A19A50/A1A090, а graph hydration делегирует scalar getters A1AC90/A1ADE0; possible late attachments и внутренний Input binding этих методов за пределами согласованного scope. Это адресные границы доказательства, **не запрос на продолжение исследования или новые функции**.

Нулевые constructor arguments не используются для отрицательного вывода. Также отсутствие прямого `FindSignal` в этих трёх функциях не означает, что такой lookup не может выполняться глубже или при позднем attachment. Напротив, proof называет точный private provider/interface, который следует отличать от публичного entity SignalsManager API.
