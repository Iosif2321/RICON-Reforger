## 0. Коротко

1. **Штатный script-путь к собственному live-audio тракту не найден и не доказан.** Публичный `VoNComponent`
   даёт `SetCapture`/PTT и `OnReceive(playerId, receiver, frequency, quality)`, но не PCM/Opus-буферы, не номера
   кадров и не veto; `VoNSystem` не имеет собственных публичных методов (только `GameSystem`). Это не доказательство
   невозможности будущих или внешних backend; внешний/нативный backend — отдельная архитектура (§6), не выбранная.
2. **Возможен и полезен собственный контур контроля над native-цепочкой**: наблюдатели движка на каждом доступном
   этапе, журнал трассы на существующих идентификаторах (epoch + linkId + binding/lease), серверная политика с
   явным охватом, адаптер актуаторов с заявленными возможностями, debug UI. Один контур служит отладке и
   настройке сейчас, а ядру — после отдельной ревизии шва (§2.4).
3. **Точечное глушение именно радиопотока A(устройство/трансивер/lease) → B(устройство/трансивер)** ни одним
   документированным актуатором не доказано (codex #3873): `SocialComponent.SetMuted` — уровень игрока, без
   устройства/канала; `BaseTransceiver.SetMuteState` — уровень трансивера, без говорящего; серверного фильтра
   получателей нет. Рассматриваемый кандидат точного **in-game** per-flow — гипотеза H6/H7 «скрытый RX на
   говорящего» (A2, §6): не доказана, с явным списком критических проверок; исчерпывающая невозможность других
   in-game вариантов тоже не доказана (codex #3890).
4. Выбор механизма — только по runtime-опытам: минимум 2 клиента (приём), для per-flow — 3 (фальсификатор).

## 2. Что такое «свой функционал» на практике

Минимальный состав (codex #3877): **один сервис управляемых направленных передач поверх S3/S3b** из трёх частей —
(1) наблюдатели движка (PTT, рация, `OnReceive`) и журнал расчётов, публикаций и отказов; (2) серверная политика
адресного block/auto/test-profile с TTL и полным binding (epoch + lease + устройства), без мутации физического
CF/seed; (3) адаптер актуаторов с явной заявкой возможностей (только radio-flow — whole-player исключён владельцем,
§7; native quality/DSP не подтверждены). Debug UI выбирает говорящего, слушающего и рацию и показывает цепь с причиной каждого отказа;
журнал — ограниченный кольцевой по выбранным парам с экспортом; серверные и клиентские времена — с источником и
неопределённостью, без фиктивной общей аудиошкалы; повтор воспроизводит расчёты по сохранённым входам и профилям,
а не native аудиопакеты. Критерии MVP (codex #3890): включение debug и частота отрисовки не меняют RF-результат,
seed, времена просветов и порядок доставки; при переполнении — явный `GAP`, а не молчаливый «полный replay».

**2.1 Журнал трассы (наблюдение).** Идентификатор трассы — существующие сущности, без второго реестра: epoch +
linkId (`REQ-link-publication.md:112–118`: ключ связи (leaseId, rxDeviceId, rxTransceiverIndex, rxPlayerId), каждый
новый PTT — новая связь) и binding/lease шва (`REQ-von-seam.md` §4: игрок/устройство/индекс с обеих сторон).
Три **раздельных** вида записей (codex #3871):
- `DESIRED` — желаемое состояние по снимку пары (LOST/WEAK/DEGRADED/CLEAN) и политике;
- `APPLIED` — фактический вызов актуатора и наблюдённое после него состояние движка (`IsMuted`, `GetRange` …);
  APPLIED означает «вызов выполнен», а не «услышано»;
- `OBSERVED` — события движка: `TX_START`/`TX_STOP` (A, `OnCapture` с идентификатором передатчика), `TX_SEEN`
  (сервер, `OnVoNUsed`), `RX_EVENT` (B, `OnReceive`: talker, receiver, frequency, quality).
Исходное время и порядок событий выбранной пары хранятся в кольцевом буфере; переполнение — явная запись `GAP`;
окна 100–250 мс — только для UI-агрегатов: по CT03 (`REQ-channel-time.md:42–47`) редкая выборка не выдаётся за
все просветы, а разрешение трассы не лучше каденции native-событий, которая неизвестна (codex #3881).
Критерий сопоставления (codex #3878): `OnReceive` не несёт linkId/leaseId/frame id, поэтому `RX_EVENT`
привязывается к трассе **только через проверенный серверный binding** (игрок, устройство, индекс трансивера);
при неоднозначности запись получает статус UNKNOWN — угадывания по частоте или времени нет.
Клиенты отправляют отчёты на сервер (RPC); сервер пишет единый лог `[RICON_CHAIN]`. Расхождения вида «RICON:
LOST, а у B есть события с quality 0.8» видны сразу — это и есть материал для калибровки и отладки.

**2.2 Реестр актуаторов (управление).** Каждый актуатор — с заявленным охватом и побочными эффектами:

| Актуатор | Кого глушит | Охват и точность для «A→B» |
|---|---|---|
| `TALKER_CAPTURE` (`SetCapture(false)` у A) | A для всех | whole-talker; не per-flow |
| `TALKER_RANGE` (`SetRange` у A, сервер) | A для всех дальше радиуса | только если все слушатели различимы одним радиусом (`LINK_CHAIN_RU.md`, «ограничение одной дальности») |
| `RX_TRANSCEIVER_MUTE` (`SetMuteState` у B) | по гипотезе H2 — всех на трансивере B | только при одном активном источнике на трансивере (H2); направление RX/TX и права не установлены |
| `LISTENER_PLAYER_MUTE` (`SocialComponent.SetMuted(A)` у B) | A для B целиком, включая прямую речь | **EXCLUDED_BY_OWNER (только радио, §7)**: whole-player глушит прямую речь; для radio-flow не доказан; строка оставлена для полноты |
| `DELIVERY_FILTER` (серверный фильтр получателей) | ровно пара и рация | идеал; хука нет — UNKNOWN |
| `A2_HIDDEN_RX` (гипотеза §6) | RX(B, A) | не доказан; gate-прототип |

Политика: снимок пары + контекст (другие активные каналы A↔B, пользовательский mute, наличие наблюдателей) →
актуатор с заявленным охватом, достаточным для команды, либо `NO_ACTION` с причиной (`SCOPE_TOO_WIDE`,
`UNKNOWN_BINDING`, `UNOBSERVED`). Молчаливой аппроксимации нет: без подходящего актуатора звук остаётся
ванильным, журнал фиксирует расхождение. По CT04 (`REQ-channel-time.md`) глушение пары — отдельная политика
поверх расчёта: дескрипторы CF, seed и потери материалов не изменяются. Блокировка оператором не записывает
физическое LOST в бюджет: модельные Q/LOST хранятся отдельно от записи `BLOCKED_BY_OPERATOR` и от попытки/наблюдения
актуатора (codex #3878). Прямая речь сохраняется — решение владельца 2026-10-23 (§7) и действующий план (`PLAN_RU.md:139`, `:448`);
whole-player режим не является выбираемым.

**2.3 Настройка.** Профили устройств и политики — конфиг с provenance (TEST_ONLY, ASSUMED_CONFIG, измерено),
которое задаётся evidence, без автоматического повышения и без скрытых констант; команды пробника (`chain show`, `block A B <device/idx> on|off`, `policy …`).

**2.4 Интеграция в ядро.** Шов `RICON_VoNIntegration` по `REQ-von-seam.md` (implementation gate, §2, §7)
остаётся stateless noop с `BLOCKED_NO_ACTUATOR` на валидном входе; CT-VON-S-010 запрещает в нём engine-API.
Новый внешний orchestrator/engine-adapter использует существующие S3/S3b и чистые проверки; переход к реальному
актуатору — отдельная ревизия REQ/seam/тестов с критериями RT/AUDIO. Сейчас обсуждается архитектура, ничего не
подключается; прежний 103/103 PASS на новый actuating-контракт не переносится (codex #3883).

**2.5 Контрпримеры (codex #3887) и вытекающие требования.**

| Контрпример | Что ломается | Требование |
|---|---|---|
| Две рации у одного A на одной частоте | B-side `RX_EVENT` даёт playerId и receiver B, но не передатчик A; ни один актуатор не разделяет два потока одного A на одном трансивере B | поток идентифицируется только A-side `TX_START` (`OnCapture(transmitter)`) + серверным lease; команда «только этот поток» → `NO_ACTION: SCOPE_TOO_WIDE` для всех актуаторов, кроме доказанного A2 |
| Смена PTT / epoch | каждый PTT — новый lease: блок, привязанный к lease, молча истекает на следующем PTT; при смене epoch состояния движка (mute) становятся сиротами | два охвата политики: per-lease (авто по снимку) и per-binding (оператор: A устройство/индекс → B устройство/индекс, epoch, TTL); при смене epoch — явная сверка `RECONCILE` всех `APPLIED` |
| Пользовательский mute | наш `APPLIED` неотличим от пользовательского; снятие сломает выбор игрока. Владение **не выводится из bool-API** (codex #3894): история 1 — RICON ставит mute, игрок ничего не делает; история 2 — RICON ставит mute, затем игрок сам ставит mute поверх; `IsMuted` и отсутствие `RX_EVENT` одинаковы, а после снятия блока RICON в истории 1 нужно false, во 2 — true | владение {NONE, USER, RICON, BOTH, **OWNERSHIP_UNKNOWN**}: читать `IsMuted` до действия, свой блок при уже заглушённом — `APPLIED_PREEXISTING`; без доказанного перехвата всех пользовательских/платформенных изменений или изолированного актуатора владение = OWNERSHIP_UNKNOWN и автоматический `SetMuted(false)` запрещён; снимать только собственную причину (codex #3882); `MISMATCH` по `RX_EVENT` — диагностика, не защита. Это gate для любого актуатора с readback-состоянием (в том числе для исключённого владельцем Social), не для набора policy-reason |
| Просвет 20 мс при редком UI | агрегат 100–250 мс стирает краткие улучшения/провалы (CT03) | сырые времена событий в кольцевом буфере, агрегаты отдельно; разрешение не заявляется тоньше каденции native-событий |
| Нет наблюдателя на одном клиенте | отсутствие `RX_EVENT` от B неотличимо от тишины | регистрация и heartbeat наблюдателей; пара без обоих наблюдателей — `UNOBSERVED`, вердикт о действии актуатора — UNKNOWN; отсутствие события никогда не трактуется как «mute сработал» |

Критерий per-flow (codex #3887): при блокировке A→B остаются A→C, C→B, B→A и другой радио/прямой путь A→B.
Испытания на одном общем RF-канале — последовательно, чтобы коллизия/полудуплекс не выдали себя за эффект mute.
Неоднозначная привязка native-события к lease/текущему потоку — UNKNOWN.

## 3. Точность глушения «A→B»

- Точный per-flow mute даёт только `DELIVERY_FILTER` (не найден) либо доказанный A2 (§6). `LISTENER_PLAYER_MUTE`
  исключён решением владельца (только радио, §7): API адресует голос игрока без канала и устройства и глушит прямую
  речь; права/направление/побочные эффекты и владение mute OPEN (`E-radio-api-s1.md:14–25`), порог прямой речи OPEN
  (`DIRECT_VOICE_RU.md`); даже как эксперимент это не точный radio-flow до AUDIO_PASS (codex #3882). Условия «вне
  дальности прямой речи, нет второго канала, нет пользовательского mute» — лишь необходимые, не достаточные.
- Фальсификатор per-flow (3 клиента): A→B LOST и C→B CLEAN на одном трансивере B. `RX_TRANSCEIVER_MUTE` заглушит
  и C — неверно; whole-player заглушит A целиком, включая прямую речь — слишком широко; верный ответ даёт только
  per-flow актуатор. Это ключевой runtime-опыт.

## 4. Риски и ограничения

- Права и authority: `SetMuted` — клиент слушающего, `SetRange` — сервер; репликация и JIP состояний; снятие —
  только собственной причины запрета, `SetMuted(false)` не универсальное безопасное завершение; при
  `OWNERSHIP_UNKNOWN` автоматическое снятие запрещено.
- Побочные эффекты: прямая речь, пользовательский/платформенный mute, другие каналы того же говорящего.
- Нагрузка: `OnCapture` каждый кадр, `OnReceive` на событие — кольцевой буфер ограниченного размера, `GAP`.
- Стабильность API: `frequency` в `OnReceive` «questionable» по словам BI; единица `GetFrequency` UNKNOWN.
- Среда: мод у всех клиентов; локальные опыты — Workbench Play/hosted; RE запрещён EULA Tools — только скрипт.
- Логи: ключи шифрования не пишутся; теги без слова FAIL.

## 8. Обновление плана (вторая задача владельца 2026-10-23)

Задача: «обновить план и продолжить разработку, опираясь на разрешённый путь DLL-интеграции / модового файла,
модифицирующего движок; проверить, можно ли модифицировать штатное радио; можно ли полностью отслеживать цепочку

Ответы по фактам §7:
- **«Разрешённый путь DLL»** в проверенных источниках не подтверждён: единственный найденный механизм native-кода —
  неофициальный interceptAR, DLL-proxy **только для dedicated server и Workbench, не для клиентов**, host закрыт «по
  юридическим причинам», лицензия/EULA/античит не оценены. Модификации клиентского движка он не даёт; доступ к VoN
  через него не подтверждён. В плане — **gate G-DLL** (codex #3937): (a) feasibility read-only — SDK, лицензия interceptAR, условия хоста,
  EULA игры и Tools, доступные точки входа — уже разрешена поручением владельца, ничего не устанавливается;
  (b) установка и минимальный опыт только в Workbench с открытым тестовым plugin — только если feasibility покажет
  реальную пользу, по отдельному решению; результат опыта — перечень доступных engine-объектов для «proto»-функций;
  (c) проверяемая гипотеза, не вывод: README подтверждает только server/Workbench, клиентский радио-hook не найден,
  но не доказан невозможным; ожидаемая польза при подтверждении — серверный C++ (расчёты, БД).
- **«Модифицировать штатное радио»** — в пределах скрипта: да, частично (`ScriptedRadioComponent`, `modded class`

  ещё не проверено (G-DLL feasibility).
- **«Полностью отслеживать цепочку A→B»** — доступные точки отслеживать можно (захват, состояние рации, «кто

  получателей в обследованном API не найдены.
- **«Влиять на цепочку A→B»** — точечно (именно эта пара, только радио) скриптом и серверной DLL не доказано;
