## Полный update: точный порядок перед program evaluation

На входе IOP runtime instance `I` проверяется byteI+38 bit0. Если bit уже установлен, управление идёт непосредственно на evaluation path9FAF71. Иначе update проходит две списка индексов:

- Первый: pointerI+98/count+A4, индексы выбирают0x20-byte records изI+8. Item pointer находится вrecord+10. На9FAF04 вызывается item virtual slot+90 сEDX=0; AL каждого вызова объединяется OR.
- Второй: pointerI+A8/count+B4, индексы выбирают0x30-byte records изI+28. Item pointer находится вrecord+20. На9FAF47 выполняется тот же virtual slot+90 сEDX=0; AL также объединяется OR.

При ненулевом суммарном AL dirty bitI+38 устанавливается. Evaluation path9FAF71 загружает program pointerI+40 и адрес stateI+58, вызывает **E9BDB0** и затем очищает dirty bit. При отсутствии dirty/change путь заканчивается RET без этого вызова. E9BDB0 здесь идентифицирован как конкретный downstream program boundary; его большой body и arbitrary opcodes не исследуются. Tail output reader9FAA10 также не экспортировался. Следующий полезный вопрос — **тип и exact slot+90 выбранного IOPItemInput**, а не весь универсальный evaluator.

Существующий frozen numerical setter9FAB40 уже даёт конкретный внешний scalar interface:0x20-byte record metadata+8 сравнивается сInputID, byte record+1C!=0 запрещает запись; иначе float записывается вrecord+18 и changed/unordered sets instance+38bit0. Для native TransmissionQuality этот setter достигается через A1B690/E9DFB0; он не получает entity/manager аргумент. Произвольное имя само не вызывает эту цепочку: публичный script должен иметь поддерживаемый доступ именно к нужному T либо должна быть доказана отдельная automatic binding/update связь. Повторный export/setter kernel не выполнялся; используется прежний [selected proof](<C:/Users/Ded/Documents/Projects/ARMA 3 Scripts/Cellular System/output/von-re-20261104/audio/REPORT.md>).

На этом шаге sender binding не установлен. Unknown late attachments продолжают означать неизвестность, а не отсутствие. Whole-event mute, Global volume и подмена Interior/RoomSize не являются допустимым bridge. Temporal contract не требует выключать native audio из q0/LOST; этот probe такой gate не добавляет.

Связь с выбранным ресурсом ограничена точно: current Von.sig сериализует обычный `IOPItemInputClass` (TransmissionQuality, id1, value1), а RTTI квалифицирует стандартный runtime Input данного типа и его update interface. Live factory population/instance contents не наблюдались; это static type qualification, не доказательство актуального mod overlay или live node pointer. В частности, функция9FAEB0 действительно вызывает slot+90 у динамических item pointers, но данным lookup не перечислены все возможные их классы и не утверждается, что любой node update возвращаетfalse.

Для стандартного Input конкретный update возвращаетfalse без чтения параметров, памяти manager или вызовов. Значение приходит через иной путь: ранее проверенный9FAB40 допускает writer вruntime scalar record+18 и устанавливает IOP dirtybit. Native receive quality уже использует его черезprivateT; публичный `BaseSoundComponent.SetSignalValue[Str]` применим к sound component, но не выдаёт ссылку на T из `VoNComponent`. Поэтому подтверждён **внешний scalar-slot interface**, а не Script SignalsManager polling внутри Input kernel. Текущего installed declaration недостаточно, чтобы адресовать arbitrary sender-private T из script; одним `AddOrFindSignal` не показано ни сопоставление manager, ни writer call.

## Что практически следует из результата

1. При создании отдельного receiver-render asset обычный Input можно использовать как control, **если** существует поддерживаемый адресуемый writer к этому экземпляру. Здесь такого handle/setter bridge к native VoN не найдено. Внутренний pointer/VA9FAB40 не является Workshop API и не предлагается к вызову из script.
2. Custom signal на sender proxy не следует считать действующим в native VoN лишь по одинаковому name или успеху SetSignalValue. Документированный SoundComponent auto binding может быть внешней update/attachment логикой, а не этим Input kernel. Возможность такой поздней связи не опровергнута, но конкретный binding writer/owner для private VoN всё ещё не показан.
3. Дальнейший общий E9BDB0 program reverse не отвечает на missing public binding и не выполняется. Следующая архитектурная зависимость — официальный per-source instance access/automatic binding contract либо отдельный разрешённый capability test того же native потока. Нужные source/listener/generation identity нельзя заменить listener-wide Global variable или acoustic signals.
4. Никакой автоматической тишины, sqelch или native delivery deny из legacy LOST/q0 этот результат не вводит. Current native q/DSP можно повторно использовать как часть receiver rendering; shared receiver front-end/interference и temporal descriptor остаются отдельным новым контрактом. Подавление всего VON_RADIO события нарушило бы сохранение Direct shader.

**Итог: precise Input-update interface counter получен; произвольный per-source/per-listener script control приватного native VoN radio DSP остаётся неподтверждённым.** Это client binding gap, не запрет temporal channel модели и не доказательство невозможности будущего официального bridge. Root получает small source facts/receipts; Ghidra, engine и SDK этим исполнителем не запускались, продуктового adapter нет.
