## Почему modded override не открывает внутренние Send/Receive

`modded` расширяет существующий script class; `override` проверяет наличие метода и совместимость сигнатуры в script base. `proto` раскрывает engine method скрипту. Эти значения определены официальными [Scripting: Keywords](https://community.bistudio.com/wiki/Arma_Reforger%3AScripting%3A_Keywords) и примером [Scripting Modding](https://community.bistudio.com/wiki/Arma_Reforger%3AScripting_Modding). Из возможности override объявленного callback не следует возможность подменить произвольный C++ метод с известным именем.

Полный установленный generated `VoNComponent` **не объявляет** `Rpc_SendVoiceData` / `Rpc_ReceiveVoiceData`, методы выбора listeners, изменения `VonContext`, список native потоков или pre-playback veto. При этом есть положительное native доказательство способа вызова: зарегистрированные VoN RPC несут `RpcPtr<VoNComponent,BitBuffer&,VonContext&>` holder; CRpc invoke `0x140D9F2D0` идёт через holder.vtable+8, adapter `0x14029DF20..0x14029DF43` — через сохранённый C++ callback к Send `0x1402A0AA0` / Receive `0x1402A0690`. Это прямой registered handler, а не вызов script метода по совпавшему имени. См. [OUTER_BOUNDARY_RU.md](<C:/Users/Ded/Documents/Projects/ARMA 3 Scripts/Cellular System/output/von-re-20261104/transport/OUTER_BOUNDARY_RU.md>) и [OUTER_SOCKET_CHAIN_RU.md](<C:/Users/Ded/Documents/Projects/ARMA 3 Scripts/Cellular System/output/von-re-20261104/transport/OUTER_SOCKET_CHAIN_RU.md>).

Следовательно, добавление одноимённого метода с новым `[RplRpc]` создаёт собственную script поверхность; оно не доказывает переназначение уже зарегистрированного native holder. Публичной операции заменить holder/его recipient condition в обследованных API нет. Попытка угадать hidden declaration, private hash или воспроизвести внутренний `BitBuffer/VonContext` не входит в supported route и здесь не предлагается. SDK compile probe с `override` мог бы подтвердить диагностическое отсутствие base symbol, но не создать missing native callback; такой probe сейчас не запускался.

Native ordering закрывает две особо правдоподобные ложные точки расширения:

- **OnVoNUsed:** в полном Send обработчике `0x1402A11B0 CALL 0x1402A04D0` выполняет recipient dispatch; только затем `0x1402A11F2 CALL 0x1402A1F00` вызывает событие. Native registry связывает event со строкой `OnVoNUsed`/global `0x142049B4C`. Изменения здесь могут влиять на дальнейшее состояние, но не являются pre-dispatch решением для уже отправленных данных.
- **OnReceive:** `0x1402A0A4A CALL 0x1407CF390` передаёт данные VonStream, после чего `0x1402A0A71 CALL 0x1402A1BE0` вызывает event, связанный с `OnReceive`/global `0x142049B48`. Ветка RX mute `+0x58` обходит CF390 и всё равно достигает события. Установленный `SCR_VoNComponent.c:78` вызывает display и `m_OnReceivedVON.Invoke(...)`; `:89` вызывает OnVoNUsed invoker. Ни одно тело не возвращает native решение.

## ScriptedRadioMessage — отдельный поддерживаемый маршрут

`BaseTransceiver.BeginTransmission(message)` / `BeginTransmissionFreq(message,freq)` проводят собственный `BaseRadioMessage` через native radio graph. Можно создать script subclass `ScriptedRadioMessage`, переопределить **объявленный** `OnDelivery(receiver,freq,q)` и внутри своего обработчика проверить RICON pair/policy перед своим gameplay действием. Это точный поддерживаемый delivery hook для собственного сообщения, полезный для radio signalling, игровых команд, тестового сообщения или отдельного AI/event сценария. Public API: [ScriptedRadioMessage](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfaceScriptedRadioMessage.html); существующий официальный пример subclass — [SCR_CampaignRadioMsg](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfaceSCR__CampaignRadioMsg.html).

Этот hook **не перехватывает ordinary microphone voice**. Native Send создаёт `VonRadioMessage` со своей delivery vtable (`0x14196B280`, delivery `0x1405E46A0`); `ScriptedRadioMessage` имеет другую vtable (`0x14196AF50`, callback adapter `0x1405E3F40`). Их общий BaseRadioMessage/общий radio graph не делает `ScriptedRadioMessage.OnDelivery` callback-ом для всех сообщений. Generated `VonRadioMessage` — пустой subclass, без публичного setter захваченного payload/списка recipients; `SoundEventPriority` явно отдельная передача AI sound event, не API инъекции microphone chunks. Полные native доказательства и pinned blob SHA находятся в relay/REPORT.md.

Минимальный будущий test здесь иной: отправить **одно собственное синтетическое** ScriptedRadioMessage между двумя настроенными native transceivers, зафиксировать `OnDelivery` и затем отказать только своему gameplay действию. PASS подтверждает этот message hook. Он не подтверждает фильтрацию захваченного player voice и не может снять `BLOCKED_NO_ACTUATOR` у обычного VoN. Создание пустого VonRadioMessage или воспроизведение sound event также не заменяет этот критерий.

## Какой официальный native контракт нужен для исходной цели

Ниже **требования к будущему официальному API**, не существующие имена методов и не предложение DLL/private bridge.

| Требуемая точка | Минимально нужный контракт | Почему существующий callback недостаточен |
|---|---|---|
| Сервер перед окончательным recipient dispatch ordinary voice | Authenticated sender + candidate receiver/device + mode, identity/generation; RICON может deny/allow только эту направленную radio-пару и передать её route/q. Правило применяется к каждому актуальному dispatch, либо его revision инвалидирует radio-recipient cache | OnVoNUsed поздний; device setters не представляют пару; собственный RPC condition не прикреплён к native descriptor |
| Клиент до применения данных к конкретному native source stream / radio render branch | Официальный handle конкретного source/route с lifetime/generation; применение radio-only gate/q до enqueue/effect для нужных samples, без изменения DIRECT и других источников. Отдельно определена судьба уже queued samples, stop/resume/expiry | OnReceive поздний, q by-value, stream handle не выдан; whole RX mute подавляет C→B |
| Lifecycle/receipt применённого решения | Missing actor, stale generation/expired snapshot не действуют на новый объект; cleanup восстанавливает только владение RICON, сохраняя user mute/power. Результат различает queued/observed/applied/unsupported | Сам custom-RPC ACK или присутствие OnReceive не доказывают native действие |

Пары в RICON уже вычисляются и публикуются существующими PairService/Evaluator/LinkPublication/SnapshotReceiver/Lifecycle. Расширение следует подключать к ним, не строить вторую таблицу решений. Требования server gate и client pre-audio в таблице разделены по способности, а не означают, что для любого применения q обязательна модификация обоих концов. **Базовое RICON q можно передать сервером в существующем native quality field и обработать штатным клиентом.** Дополнительный client pre-audio контракт нужен для более сильных гарантий: немедленный отзыв перед проигрыванием, корреляция поколений пакетов/решений и управление уже накопленным звуком. Минимальный серверный вариант ниже сохраняет это различие.

В native map один listener record может получить сначала DIRECT, затем radio metadata с overwrite. Поэтому будущий серверный gate должен применять решение к radio contribution, сохраняя независимую direct contribution. Одновременно текущий ACP `VON_RADIO` связывает **Radio и Direct** shaders: один network record не означает один акустический путь. Нельзя квалифицировать audio-only решение по подавлению всего `VON_RADIO` события. Результат asset-разбора принадлежит отдельной роли; здесь это обязательное условие интерфейса, не новый DSP adapter.

## Минимальный серверный API: radio candidates и штатное q

Это **проект границы API для официального расширения native server code**, не работающий adapter и не найденный Workshop hook. Существующие клиенты уже принимают тот же encoded voice payload и `VonContext.quality`; менять codec, packet schema и client DSP для этого базового варианта не требуется по статической цепочке данных. Реальную совместимость версий и слышимый результат ещё должен подтвердить квалификационный тест. Установка DLL, перезапись vtable/handler и private RPC в этот проект не входят.

Точка расширения — **формирование radio candidate population до её объединения с DIRECT**, то есть до применения radio delivery к общей listener map. Это семантическая граница двух вкладов. В текущей реализации хронология иная: DIRECT records уже созданы, затем radio delivery вставляет/перезаписывает запись того же listener. Поэтому расширение должно подменять/дополнять radio population перед этим overlay, а не удалять из готовой общей map запись запрещённого radio-получателя. Последнее уничтожило бы допустимый DIRECT-вклад той же пары.

```text
owner-authenticated voice + native source TX/device
     ├─ native DIRECT candidates ───────────────────────────────┐
     └─ RICON radio population: candidate RX + final q/frequency │
          → native terminal frequency/key/self filter          │
          → native radio delivery / receiver resolution        │
          → native listener merge (radio overlay) ──────────────┘
          → native bilateral Social gate / receiver RPC
          → обычный клиент: native decode/queue + штатное q/DSP
```

Граф — proposed insertion point внутри уже доказанной цепочки. Он не объявляет существующую script функцию с таким именем и не отменяет независимые native owner/mode/receiver/lifecycle проверки. Точный downstream контракт подтверждён в [CONTEXT_STAGES_RU.md](<C:/Users/Ded/Documents/Projects/ARMA 3 Scripts/Cellular System/output/von-re-20261104/transport/CONTEXT_STAGES_RU.md>): quality `context+0x00` приходит из radio delivery; source frequency занимает `+0x04`; delivery отдельно переписывает radio ID/index на **приёмные** `+0x0C/+0x14`. Эти стадии сохраняются, их нельзя заменить копией TX metadata в RX context.

Минимальный контракт границы:

| Часть API | Требование к поведению |
|---|---|
| Вход | Уже аутентифицированный ordinary sender, выбранный native TX, текущие endpoint identities/generations, snapshot revision и исходный mode. Входные client q/псевдо-identity не являются истиной |
| Выход | Актуальная radio population: конкретные допустимые native RX endpoints и **конечное per-pair q** с конечным числом в штатном диапазоне `[0,1]`; source-hop frequency соответствует native radio semantics. Deny означает отсутствие radio contribution этой пары, а не `q=0` и не удаление общей DIRECT-записи |
| Population authority | Если задача включает маршруты вне stock graph/range, API должен принимать собственную population RICON или согласованный union. Только фильтрация stock найденных candidates не создаёт новые RICON маршруты; такой более узкий API следует честно обозначить filter-only |
| Native reuse | Конечные native key/frequency/self filters, receiver-component resolution, listener merge, bilateral Social predicate, owner checks и receiver RPC сохраняются. RICON allow не обходит native deny. Несовместимый с terminal frequency/key маршрут требует отдельного явного контракта, а не скрытой смены частот/ключей |
| Quality ownership | RICON q подаётся в фактическую radio delivery quality record до её копирования в `context+0x00`; stock graph/recomputed distance q не должен перезаписать это значение после API. При нескольких RX/routes одного listener нужны явно заданные выбор endpoint и q: текущий map merge может перезаписать предыдущую запись, он не гарантирует глобально лучшее q |
| Cache/lifetime | На каждом dispatch учитывается текущая policy, либо изменение snapshot revision, expiry и endpoint generation обязательно инвалидирует/revalidates cached population. Недостаточно ждать native движения/retune. Stale endpoint нельзя заменять новым actor с тем же player/device id без новой проверки |
| DIRECT/user state | Radio deny не модифицирует DIRECT construction/template и не снимает user mute/power/ownership. Сохраняются штатные mode-specific правила, без GM/editor подмены. Разные render branches `VON_RADIO` дополнительно проверяются на клиенте, а не выводятся из количества map records |

**Граница доступности:** native-code-feasible point установлена доказанной структурой population→delivery→merge→RPC; это обоснованный проект расширения движка. Workshop-accessible hook для подмены этой population/quality сейчас **не найден** в проверенных declarations. `BeginTransmission(ScriptedRadioMessage)` не предоставляет эту точку для microphone data, а собственный `[RplRpc]` не меняет native population. Поэтому этот дизайн не снимает текущий `BLOCKED_NO_ACTUATOR` и не является обещанием реализации только Enforce Script.

**Граница отзыва:** server deny прекращает последующие допустимые radio dispatch после применения новой revision. Он не отзывает уже отправленные/in-flight voice packets, pending encoded chunks клиента, decoder/PCM queue и render/device tails. Смена q также распространяется с доставкой и штатной обработкой, а не обязательно в момент изменения RICON policy. Stop/final byte существующего voice context не является подтверждением очистки этих очередей; неиспользованные context bytes нельзя считать готовым полем generation.

Если требуется **hard client pre-playout revoke**, нужен дополнительный официальный client pre-audio контракт: корреляция source/route/decision generation с принятыми пакетами, отбрасывание устаревших samples до нужной radio render branch и определённая очистка принадлежащих ей pending/PCM samples. Будет ли достаточно локального state lookup без изменения wire или понадобится передавать generation — отдельный дизайн после формулировки точной гарантии; существующий context сам такую корреляцию не доказывает. Уже выданные OS/device samples задают физическую границу отзыва. Серверный вариант не обещает instant silence.

Минимальная будущая квалификация этого дизайна: на неподвижных A/B/C изменить только RICON revision A→B, проверить отсутствие **новых radio contributions** после точки применения revision, сохранность DIRECT A→B, C→B того же RX и A→C; затем подтвердить, что RICON q достигает штатного quality field у обычного клиента. Отдельно измерить доставку ранее отправленного/очередного аудио после deny и записать хвост, не объявляя его нарушением более слабой server-dispatch гарантии. Если продукт требует жёсткого отзыва, тот же хвост становится отдельным критерием для client pre-audio extension, а не причиной приписать серверу отсутствующую возможность.

## Самая маленькая будущая квалификация

Сейчас выполнены чтение declaration/body, проверка существующих native call sites и актуальная сверка public API. Код игры/адаптера не менялся; SDK compile, Play, server, capture и packet/audio тесты **не выполнялись**. Callback availability и native audio actuation имеют разные результаты проверки.

1. Получить от официального SDK/API конкретную объявленную серверную population/quality точку; при требовании hard revoke дополнительно квалифицировать client pre-audio/generation контракт. Перед реализацией adapter проверить точные signature, доступность в game runtime установленной версии и минимальный официальный пример. Если есть только observers/setters/current custom RPC, результат этой проверки — `NO_SUPPORTED_PAIR_HOOK`, а не зелёный actuator.
2. После отдельного разрешённого runtime этапа использовать A,B,C: B слушает A и C **на одном RX**, A→C здоров; A расположен также в DIRECT слышимости B. Менять только RICON решение A→B: baseline → deny → restore, затем high-q → low-q → high-q. Для server hook фиксировать отсутствие только radio dispatch A→B до отправки; для audio hook — конкретное изменённое radio звучание только A→B. Логи OnReceive/успешный setter/custom RPC сами по себе не PASS.
3. Во всём цикле C→B, A→C и A DIRECT→B остаются доступны. Отдельно повторить native cache reuse с неподвижными устройствами, изменение RICON revision без движения, retune/power/user mute; затем respawn/missing actor, stale/duplicate snapshot и expiry. Обработчик не пишет за чужую generation, не снимает user mute/power, не оставляет блокировку после cleanup. Observer subscription удаляется при lifecycle cleanup.
4. Остановить candidate при первом scope violation: whole RX mute, весь TX stop, пропавший DIRECT, stale actor mutation или эффект только после уже обработанного пакета. Сохранить конкретную причину отказа; не компенсировать её GM/editor режимом, Interior/RoomSize, private hashes или альтернативным voice backend.

**Рекомендованный следующий шаг:** запросить/спроектировать официальный серверный API подмены radio population и конечного q перед radio overlay в listener map с cache/lifetime контрактом и сохранением native downstream. Это минимальный вариант повторного использования ordinary clients. Требование hard pre-playout revoke/packet-generation correlation оформить отдельно; при нём нужен дополнительный client pre-audio контракт. Параллельно существующие supported observers и собственный script RPC пригодны для shadow/control qualification уже имеющегося RICON pipeline. До появления и квалификации actuator сохранять `ApplySnapshot = BLOCKED_NO_ACTUATOR`; отдельные успешные control/message тесты эту границу не снимают.
