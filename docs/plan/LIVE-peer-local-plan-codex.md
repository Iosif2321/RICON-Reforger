# Локальная проверка двух ролей через Diag и PeerTool

Дата: 2026-10-24, уточнение сетевого режима 2026-10-25. Автор: codex. Продолжение после взаимной приёмки A1-S2/Q-F
(agora #4516, #4521; порядок работ #4524). Статус: **план и факты взаимно проверены
(#4551); источник PeerTool прочитан, клиент ещё не запускался**.

## Результат следующего среза

Проверить одну пару процессов на этом ПК: текущий Workbench в роли authority и
один установленный Diag-клиент, подключающийся к этому же ПК по проверенному локальному адресу. Получить наблюдения
двух разных игровых ролей и игроков. Это подготовка сетевого стенда; голос,
слышимый mute, репликация флагов трансивера и точечное A→B здесь ещё не принимаются.

Постоянное разрешение владельца на необходимые действия действует. Новый запрос
разрешения на локальный процесс не нужен; остаётся согласование конкретного
эксперимента между операторами через START/ACK/END. Параллельный A0-M ведёт claude.

## Проверенные основания

- Установлены `ArmaReforgerSteamDiag.exe` (40 060 472 байта) и
  `ArmaReforgerWorkbenchSteamDiag.exe` (67 576 376 байт); FileVersion и
  ProductVersion обоих — 1.8.0.13. Отдельная установка Server не обнаружена.
- [BI: Development Executables](https://community.bistudio.com/wiki/Arma_Reforger%3ADevelopment_Executables)
  описывает отдельные Diag-версии клиента и сервера. Для этого опыта выбираются
  согласованные Diag-версии; отключение проверок совместимости не требуется.
- Установленный SDK: `EnfusionScriptAPI/html/interfacePeerPlugin.html` и
  `interfacePeerConfig.html` — Executable, PeersWindows, Start/End, Profile,
  Params, RplAutoJoin, размеры окна и MaxFPS. Документация указывает PeerTool.c.
- Штатный файл найден в `$core:scripts/WorkbenchGameCommon/PeerTool.c`, CRC
  `d12a9aa0` в проверенном compile-логе S2. Поиск в `$ArmaReforger:scripts`
  корректно вернул ноль кандидатов. Шесть чтений через ScriptEditor — без мира,
  без запуска клиента, не более 15 строк за запуск; [квитанция](../evidence/receipts/peer-source-review-codex.json).

По прочитанным окнам PeerTool:

| Место | Факт |
|---|---|
| 1–5 | Назначение — запуск peer-клиентов к текущему Workbench; путь Executable задаётся настройкой. |
| 65–79 | Используются GetAddonsDirCLI/GetAddonsCLI и текущий gproj; запускаются только Enabled-конфигурации, индексы профиля начинаются с 1. |
| 80–94 | Добавляются каталоги/ID аддонов, оконный режим, позиция, размер и ограничение FPS. |
| 99–107 | AutoJoin добавляет `-client`; остальные опции — reconnect, отключение timeout и отдельный профиль с индексом. |
| 108–122 | Params дополняет команду; запуск выполняет Workbench.RunProcess, пустой handle регистрируется как ошибка. |

[BI: Startup Parameters](https://community.bistudio.com/wiki/Arma_Reforger%3AStartup_Parameters)
подтверждает явный `-client 127.0.0.1`, перечень GUID в `-addons`, дополнительные
каталоги в `-addonsDir`, отдельный путь `-profile` и `-noBackend` для отключения
обращений к backend. Значения с пробелами должны быть заключены в кавычки.

## Кандидат команды и обязательная подготовка

Ниже схема аргументов, **не исполненная команда и не доказательство подключения**:

Предпочтена ручная сборка аргументов с явным адресом. Это производный диагностический
запуск: штатный AutoJoin в PeerTool добавляет голый `-client` без адреса.
**Уточнение после B0a-on:** пример `127.0.0.1` из Startup Parameters относится
к описанному там локальному dedicated server. [Документация World Editor](https://community.bistudio.com/wiki/Arma_Reforger%3AWorld_Editor)
выделяет режимы Server localhost / Server localhost + PeerTool и указывает для
них прямой адрес компьютера, а не loopback. Поэтому прежний выбор `127.0.0.1`
для Workbench не считается подтверждённым; адрес надо определить отдельно.
Обычный Play пока наблюдался только с rplMode=0 и isServer=1 — это не доказательство
готового слушающего сервера. Настройка Server localhost проверена Off → On → Off
без Play (2026-10-25, Agora #4691/#4696); затем в опыте 125954 наблюдалось начало
Listen, но полный цикл не завершён (подробности в конце документа).

```text
"<установленный ArmaReforgerSteamDiag.exe>"
  -gproj "<текущий RICON_LiveProbe/addon.gproj>"
  -addonsDir "<точный результат GetAddonsDirCLI текущей сессии>"
  -addons "<точный результат GetAddonsCLI текущей сессии>"
  -window -screenWidth 960 -screenHeight 540 -maxFPS 20
  -client <подтверждённый адрес выбранного серверного режима>
  -profile "<новый отдельный каталог RICON_peer_<run>_1>"
  -noBackend -logsDir "<уникальный журнал клиента>"
```

До START конкретного запуска нужно получить фактические addon-аргументы из того
же проекта, определить локальный endpoint Workbench и подготовить наблюдатель
клиентской роли. Параметры reconnect, отключение timeout и проверок ресурсов/скриптов
для первого опыта не включаются. Значение MaxFPS — запрошенный предел, фактическая
нагрузка им пока не подтверждена.

В прочитанном PeerTool не добавляет кавычки вокруг addonsDir, addons и profile.
Возвращает ли GetAddonsDirCLI уже закавыченную строку, ещё не установлено. В наших
путях есть пробелы, поэтому готовые строки нельзя повторно разбирать по пробелам
или слепо объединять: конкретная команда должна сохранить каждый аргумент целиком.
Параметр `-noBackend` документирован BI для игрового exe, но его действие в этом
клиенте ещё не проверено; `-logsDir` исполнялся в наших Workbench-прогонах, а место
и свежесть журнала отдельного Game Diag нужно подтвердить первым запуском.

Текущий `RICON_LiveRadioBenchComponent` создаётся launcher-ом на временной сущности
Workbench. Нельзя предположить, что эта сущность или её компонент автоматически
появится у клиента. До сетевого запуска необходимо выбрать и проверить штатный
Game-side способ включения наблюдателя на клиенте; Workbench-плагин в отдельном
игровом exe такой способ не заменяет. Приоритет — переиспользование
`RICON_LiveProbeComponent`/наблюдателя, без изменения production VoN seam.
Если потребуется новый callback, сначала читается его жизненный цикл и проводится
компиляция. Создание второго процесса без такого наблюдения даст лишь диагностику
запуска, а не приёмку двух игровых ролей.

## Порядок и критерии

1. Сверить текущий снимок аддонов и команды обоих процессов, заранее определить
   их разные каталоги профилей и журналов. Не использовать пользовательские
   конфигурации PeerTool как неявный источник Params.
2. Запустить один согласованный Workbench-мир; подтвердить authority, локального
   игрока и доступный локальный endpoint. Отдельно согласовать ожидание от Plain:
   пока не доказано, что его игровой режим корректно обслуживает второго игрока.
3. Запустить один Diag-клиент через подтверждённую команду, с явным локальным адресом
   этого ПК, соответствующим выбранному серверному режиму.
   Наблюдать не более 90 секунд после готовности мира; при неизвестном окне или
   ошибке загрузки остановить собственные процессы. Ограничить число процессов
   заранее; завершать только PID, полученные при этом запуске.
4. На сервере подтвердить появление второго игрока; на клиенте — клиентскую роль,
   свой PlayerController/PlayerId, управляемую сущность и радио-entry. Сопоставить
   личности между журналами. Два окна или успешный Start-Process не заменяют эти факты.
5. Зафиксировать raw-логи, SHA, версии, результаты загрузки аддонов и роли. Партнёр
   независимо проверяет полный набор. При нехватке наблюдений — NOT_READY с причиной.
6. После этого отдельным планом включить наблюдатели захвата/приёма и проверить H2.
   Для A→B LOST одновременно с C→B CLEAN требуются три различимые роли; текущая
   пара процессов не закрывает этот критерий.

В этом документе не утверждаются доступность второго голосового источника,
работа нескольких Steam-ролей, доставка VoN, права клиента на SetMuteState или
производительность. Подготовленный путь уменьшает неопределённость среды,
но не заменяет ни один из этих опытов.

## B0b: следующий исследовательский срез после B0a

B0a взаимно принят (#4606, STATUS 98e46f2): Game-side наблюдатель проверен в
Workbench с гейтом выкл/вкл и при повторном Play. Он ещё не проверен в отдельном
клиенте и не устанавливает, как устроен фоновой сервер Workbench.

1. Read-only уточнить способ выбора **Server localhost** в установленном World
   Editor: точное действие UI либо подтверждённый API/параметр, а также различие
   с обычным Play и с Server localhost + PeerTool. Установить смысл чисел RplMode
   по установленному API/исходнику. Не менять режим догадкой по isServer=true.
2. Подготовить один ограниченный опыт выбранного серверного режима. До START
   определить, какие процессы он может создать, как отслеживаются их PID и как
   они завершаются. Наблюдать фактические роли и отдельность журналов; не считать
   один PID гарантией одного игрового контекста. Передача нашего CLI-гейта в
   автоматически созданный фоновой процесс тоже требует наблюдения.
3. Снять фактический адрес/endpoint и режим репликации. В SDK есть
   `RplSession.TryGetListenAddress()`; его результат — диагностическое значение,
   а не доказанный приём соединения. Сопоставить его с ролью и сетевыми данными
   собственного процесса. До этого не выполнять старый шаблон с 127.0.0.1.
4. После независимого ревью этих фактов — отдельный план одного Diag-клиента:
   точная команда, кавычки, согласованные аддоны, новый профиль, собственный лог,
   проверка роли/PlayerId и его принадлежности серверному members. Сбор хоста
   должен продолжаться во время подключения: уже завершившийся журнал B0a не
   подтверждает последующее соединение.
5. Только после наблюдения обеих ролей переходить к подпискам VoN и акустическому
   опыту. Данные о частоте и IsMuted не заменяют доказательство слышимости.

Автоматически запускаемые процессы PeerTool включаются в заранее определённый
набор процессов и ролей. Перед каждым экспериментом фиксируются снимок кода,
команда, START/ACK операторов и ограничение времени; разрешение владельца уже есть.

### Уточнение после проверки меню, 2026-10-25

Шаг 1 закрыт на уровне UI: `Game → Play Game Options → Server localhost`.
InvokePattern меняет только этот пункт и возвращает исходное состояние; TogglePattern
в отдельном опыте не дал эффекта. Оба опыта прошли без Play и новых процессов;
[независимое ревью](../evidence/E-b0b-operator-review-codex.md).
Enum проверен нативно: None=0, Client=1, Listen=2, Dedicated=3.

Для шага 2 выбран штатный `Game → Play Game` после чтения Server localhost=On,
PeerTool=Off. Launcher регистрирует наблюдатель, открывает Plain без сущностей
стенда и сохранения, ждёт внешний Play до 120 с. После 30 срезов или 45 с
наблюдения возвращает edit; устойчивость edit проверяется прежними 51 чтением
за не менее 5 с. Оператор восстанавливает настройку только после EDIT_STABLE
и свежего полного снимка. Таймаут или неизвестное состояние не считаются успехом.
До взаимного ревью кода и отдельного START/ACK этот опыт не выполняется.

Первый опыт 125954 установил начало Listen (2), наличие адреса в API и строку
движка о прослушивании ANY:2001. Полный шаг 2 ещё не закрыт: синхронный UIA-вызов
Play блокировал управляющий цикл; срезов и возврата нет. Последующий осмотр
130447 подтвердил исходную настройку Off. Согласована минимальная правка:
Invoke в отдельном runspace, существующий цикл продолжает наблюдать окна,
процессы и сеть; Play не повторяется. Затем новый ограниченный опыт.
Наблюдение Listen пока не разрешает считать шаг 3 (сопоставление адреса) или
подключение Diag-клиента пройденными.

В повторе 131244 асинхронный Invoke позволил увидеть заголовок Script Authorization
Required, но чтение окна через UIA завершилось таймаутом. Следующий согласованный
путь A2 (4a0589d, source принят #4748): после проверки Server=On оператор создаёт
через CreateNew отсутствующий `tools/RICON_LiveProbe/ops/RICON_B0b_start.flag`.
Launcher с `-riconBenchStartFlag=1` ждёт его до 120 с и вызывает SwitchToGameMode
один раз. Runner больше не вызывает UI Play; файл удаляется только если этот
runner его создал. Заранее существующий файл означает отказ. Компиляция A2
прошла, реальное чтение сигнала и сохранение выбранного Listen ещё не проверены.

Опыт 172649 показал повторную авторизацию FileExists после разрешения :187;
файловый опрос больше не используется. Новый согласованный путь (#4850):
runner проверяет исходные настройки, включает только Server localhost, затем
находит единственный пункт **Plugins → RICON: Play** и вызывает его. Run
передаёт однократный сигнал в памяти, ожидающий поток launcher начинает Play.
CLI: `-riconBenchPluginStart=1` с inspect+probe. FileIO и файлы-сигналы не нужны.
До PLUGIN_SEEN разрешений не нажимаем; затем допускается только прежний точный
запрос арсенала, один раз. Сначала требуется живое подтверждение пункта меню,
быстрого возврата Invoke, срезов и возврата в edit. Компиляция и четыре проверки
допуска/однократности сигнала прошли в 173944, сам игровой путь ещё не проверен.

### B0b подтверждён; следующий срез B0c

В 175912 игровой путь с командой плагина прошёл: Server localhost / Listen,
30 срезов, один локальный игрок, UDP ANY:2001 по измерению оператора,
EDIT_STABLE и восстановление всех десяти настроек. Независимый checker codex
подтвердил 35 событий без потерь и равенство stream/dump; [результат](../evidence/receipts/b0b-host-cycle-review-codex.json).

До B0c нужно определить ровно один управляемый клиент. Простое переключение
на Server localhost + PeerTool без проверки конфигурации недостаточно: заранее
проверяются Executable, список Enabled, Params, профиль, аргументы аддонов и
завершение процесса. Уже прочитанный PeerTool передаёт Params; наследование
произвольных CLI-флагов хоста не доказано, поэтому endpoint-probe задаётся явно.
Вариант ручного Diag-запуска остаётся альтернативой, выбор ещё не зафиксирован.

Критерии B0c: клиент Mode=Client и собственный PlayerId; сервер одновременно
видит этого игрока в members; журналы обеих сторон привязаны к одному опыту,
наблюдение хоста продолжается во время подключения и после него. Текущие
30 срезов/45 с до возврата требуют проверки достаточности для старта клиента.
Слышимый голос и per-pair mute не входят в приёмку самого соединения.

Выбран первый вариант B0c: ручной запуск одного Diag-клиента с отдельным
временным профилем; сохранённые настройки PeerTool не меняются (#4889–4890).
2026-10-25 повторно сверена [официальная документация World Editor](https://community.bistudio.com/wiki/Arma_Reforger%3AWorld_Editor):
для Server localhost указан реальный адрес компьютера, не loopback.
Поэтому привязка ANY:2001 не меняет выбор адреса на 127.0.0.1.
Параметры окна и noFocus подтверждены [Startup Parameters](https://community.bistudio.com/wiki/Arma_Reforger%3AStartup_Parameters);
смещение окна не считается доказанным способом скрыть его.
Сущность серверного стенда для запуска клиентского наблюдателя не требуется
по текущему исходнику: он находится в modded ArmaReforgerScripted. Исполнение
этого наблюдателя в отдельном клиенте ещё не подтверждено.

### Исполнимый план B0c, 2026-10-25

Согласование: Agora #4906–4908. Окно отдельного клиента разрешено владельцем
(#4901). Владение: codex — Probe, launcher, нативная самопроверка и этот план;
claude — операторские скрипты, адрес, профиль и процессы. PeerTool не включаем.

1. Хост запускается прежним способом через `RICON: Play`, с добавлением
   `-riconEndpointSamples=120 -forceUpdate`. По умолчанию остаётся 30 срезов;
   допустимы только 30 и 120. Журнал ограничен соответственно 256 и 1024
   событиями. Launcher ждёт выбранный лимит с запасом 15 секунд, затем
   выполняет прежний возврат в edit и проверку его устойчивости.
2. Перед стартом клиента должны одновременно выполняться условия: есть
   PLAY_ENTERED и Listen, цикл хоста ещё не завершён, у его PID сейчас открыт
   UDP-порт 2001. Историческая запись об этом порте не заменяет текущий снимок.
3. Клиент запускается только один раз. Адрес — единственный PRIVATE_V4,
   Preferred, DHCP на активном интерфейсе со шлюзом. Непосредственно перед
   запуском проверяется, что выбор не изменился. При отказе клиентская часть
   не запускается, а хост восстанавливает настройки.
4. Используется установленный ArmaReforgerSteamDiag.exe версии 1.8.0.13 и тот
   же gproj LiveProbe. Рабочая папка — корень репозитория. В addonsDir явно
   включаются каталоги игры, Tools, repo/addons и repo/tools. Probe включается
   явным параметром, лимит клиента остаётся 30. Отдельная сущность сервера ему
   не требуется по исходнику; загрузку скриптов подтвердят CRC в журнале.

Схема аргументов первого клиента (выполнена в 202016):

```text
-gproj "<LiveProbe/addon.gproj>"
-addonsDir "<каталоги игры, Tools, repo/addons, repo/tools>"
-client <подтверждённый локальный IPv4>
-profile "<новый каталог в scratchpad>"
-logsDir "<отдельный абсолютный каталог журнала>"
-window -screenWidth 960 -screenHeight 540
-maxFPS 20 -noFocus -forceUpdate -noBackend
-logLevel verbose -log-scr-checksum -riconEndpointProbe=1
```

Форма `-client <IPv4>` документирована; первый прогон 202016 подтвердил
подключение к порту 2001 без добавления порта к аргументу. Абсолютный logsDir
и смысл profile подтверждены
[официальными параметрами запуска](https://community.bistudio.com/wiki/Arma_Reforger%3AStartup_Parameters).
Таймауты и проверки совместимости ресурсов не отключаются.

Оператор удерживает отдельный Process handle клиента; это второй собственный
корень, а не потомок WB. Его дочерние процессы фиксируются с доказательством
владения; в первом опыте их появление останавливает клиентскую часть.
Неизвестные запросы разрешений не нажимаются. Ввод клиентскому окну не нужен.
Ошибка клиента не должна мешать откату настройки хоста. При завершении
сначала останавливаются клиент и его подтверждённые потомки, затем WB.
Сторож не отменяется, пока выход соответствующего процесса не подтверждён.
Общий предел опыта — 300 с, сторож хоста — 330 с.

Успех B0c требует Mode=Client и положительного PlayerId клиента, отличного от
локального ID хоста; хост одновременно видит этот ID в members не менее пяти
последовательных срезов. Сопоставляются именно журналы одного опыта, включая
неожиданные разрывы. Наличие управляемой сущности и рации — отдельные признаки;
их отсутствие не подменяет результат проверки самого соединения. Голос и
слышимое подавление A→B по-прежнему вне приёмки B0c.

Нативная часть подготовлена и принята по исходнику (#4914). Компиляция 192930:
SCRIPT(E)=0, enum 4/4, сигнал 4/4, выбор лимита 8/8, 19 исходников стабильны.
[Квитанция](../evidence/receipts/b0c-compile-codex.json). Игрового запуска B0c
и отдельного клиента в этой проверке не было.

### Результат первого B0c и следующий кандидат

202016 завершился с восстановлением хоста, но B0c не принят: соединение
прошло загрузку мира и валидацию, затем сервер отклонил клиента как дубликат
личности. Во всех 120 срезах хоста остался один игрок. Отдельный профиль
в данном опыте не дал отдельного имени. [Разбор и границы доказательств](../evidence/E-b0c-client-codex.md).

В установленной официальной документации SDK найден `-username` с
назначением для нескольких локальных тестовых клиентов (ENF_DEVELOPER).
Следующий кандидат — `-username RICON_B0c_peer1` только в аргументах клиента;
применение параметра и отличие PlayerId ещё надо наблюдать. Проверки
идентичности сервера, совместимости данных и имя Steam-аккаунта не меняются.
