## 2. Что действительно обещают API

- **W1 — [Sleep](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-sleep), [Scheduling priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities).** После timeout поток ready, но не гарантирован его немедленный запуск. Более высокий priority может вытеснять низкий. QPC измеряет задержку, но не заставляет поток исполниться; увеличение priority/timer resolution не доказательство D150 и здесь не предлагается.
- **W2 — [QPC](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps).** Same-system timestamps согласованы между процессами; frequency постоянна в boot, межпоточный порядок ±1 tick неоднозначен. Это контракт измерения, не scheduler deadline и не связь с clock игры.
- **W3 — [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=netframework-4.8).** Внешнее завершение асинхронно; exit требует завершения/cancel pending IO. Успешный command-return не exit и не native release. В смешанной .NET странице применим здесь только Kill(), не tree-overload.
- **W4 — [Process handles](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers).** CreateProcess возвращает process/thread handles; handle валиден до закрытия даже после exit. Это основа безопасной адресации вместо повторного PID lookup, но не доказательство наличия такого пути в будущей PowerShell реализации.
- **W5 — [GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow), [GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid).** Получают текущий HWND и creator PID/TID; foreground может быть NULL, invalid HWND даёт ошибку. Последовательные calls не атомарная гарантия будущего фокуса, PID не held handle. Это кандидаты для отдельного разрешённого adapter, не уже доступный PS/Enforce bridge.
- **W6 — [Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [basic limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).** KILL_ON_JOB_CLOSE действует при закрытии последнего job handle; зависший, но живой держатель не обязан его закрыть. Time limits — user-mode execution time, проверяемое периодически, не wall-clock deadline. Принадлежность/children/breakaway надо проектировать; это не разрешение tree kill и не готовый ответ D150.
- **W7 — [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).** Описаны flush и caching, не численная worst-case latency. Это не доказательство семантики Enforce IO.
- **E1 — [System.GetTickCount](https://community.bistudio.com/wikidata/external-data/arma-reforger/EnfusionScriptAPIPublic/interfaceSystem.html#a5a202e5ab22d99955ca6ea9df97e4fda).** Milliseconds since game started, return int; не документированы QPC epoch/mapping, drift bound и нужная K0 wrap/error decomposition.
- **E2 — [FileIO](https://community.bistudio.com/wikidata/external-data/arma-reforger/EnfusionScriptAPIPublic/interfaceFileIO.html), [FileHandle](https://community.bistudio.com/wikidata/external-data/arma-reforger/EnfusionScriptAPIPublic/interfaceFileHandle.html).** Есть OpenFile/Write/WriteArray/Close, но эти страницы не задают sharing/visibility/flush deadline или nonblocking contract. WriteLine добавляет **CR+LF**, тогда как proposed wire требует LF; механическое применение WriteLine не реализует exact framing. Write с длиной — кандидат, не доказательство UTF-8 bytes/атомарности. В показанном FileHandle API нет метода Flush; выдумывать его нельзя.

## 4. Проверяемые контрпримеры, не исполненные тесты

1. **Планировщик.** Все prechecks успешны; непосредственно перед due watchdog не получает CPU 500ms. QPC корректно покажет превышение после возобновления, но не предотвратит его. То же возможно у второго user-space watchdog; N0 до этого может быть идеальным. D150→hard-bound не доказан.
2. **IO и последовательность.** После принятого frame safety thread вошёл в синхронный read/flush/check либо первый command и не вернулся. Внутренний timeout/finally на том же потоке не исполняется; правило «не ждать exit первой роли» не спасает от отсутствия return первого call. Отдельный IO worker убирает одну зависимость, но не общий scheduler/host failure.
3. **Focus/provenance.** A foreground при samples t=0 и200ms, другое окно активно между50 и150ms; UP попадает в иной контекст либо не наблюдается A. Два хороших снимка не различают этот trace и непрерывный фокус. Наличие одного listener DOWN/UP отдельно не атрибутирует единственного физического автора.
4. **Квота/exit.** Engine пишет большой burst после последней size check; до следующей проверки tool cap цел. Поздний Kill не отменяет уже записанные bytes; успешный Kill return с pending IO не доказывает своевременный exit. Это разные обязательства, не один cleanup PASS.

Числа примеров — аналитические witnesses, не измерение текущей машины. Corrected budget100+1500+150+50=1800ms и резерв200ms арифметически согласован. REQ уже правильно называет N/D/E **run acceptance thresholds**, а не Windows guarantee. Проблема не в сумме: до ARM требуется независимый safety case, а покрытие названных отказов текущими средствами отсутствует. Нельзя сделать threshold предпосылкой, доказанной будущим успешным опытом.

**Если требуется безусловная защита при host/IO/watchdog hang, исходный physical acceptance неисполним в выбранном user-space контуре.** Это не утверждение, что REQ обещает universal real-time: он прямо запрещает такое обещание, но требует предварительный safety case и оставляет отсутствие защиты blocker-ом. Если достаточно bounded observed outcome с принятым остаточным риском, нужна утверждённая смена модели отказов; reviewer её не делает. Для продолжения нейтральной работы менять physical contract не требуется.
