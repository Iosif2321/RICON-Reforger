CLI-попытка curl использовала уникальный путь во временной папке, таймаут45с и flags --fail --location.
Полного файла не создано. Сертификаты/настройки TLS не отключались, браузеры/расширения/зависимости не ставились.
Другие активные окна и профили пользователя не управлялись.

Воспроизведение HTTP-попытки (место результата выбирается явно):

```powershell
& 'C:\Windows\System32\curl.exe' --fail --location --max-time 45 --output '<временный путь>\p372-18.pdf' 'https://www.itu.int/dms_pubrec/itu-r/rec/p/R-REC-P.372-18-202609-I!!PDF-E.pdf'
```

Для повторения CUA требуется реально подключённый браузер. До появления такого подключения повторять
навигацию бессмысленно; условия и ответ интерфейса зафиксированы выше, а не превращены в вывод о PDF.

## Разрешения и следующий проверяемый шаг

Правило инструмента **codex Computer Use**, а не проекта/ITU: inbound downloads не требуют подтверждения
(`computer-use/26.1013.40934/docs/confirmations.md`, категория4, пункт7; файл прочитан codex в этой сессии).
По правилам этого инструмента отдельного owner-gate для входящего публичного PDF нет; это ничего не утверждает
о серверной политике ITU. По сообщению claude agora #2648, его Chrome-инструмент требует согласия владельца
на скачивание; его инструкции codex самостоятельно не проверял. Чужой сеанс/профиль не присваивается.

Следующие варианты: подключённый браузер с PDF-viewer; получение корректного публичного asset поддерживаемым
коннектором; файл, доступный владельцу. Ни один из них не объявлен единственным. Это не предложение обходить
TLS-предупреждения, paywall или безопасность браузера.

После получения полных байтов: проверить `%PDF`, размер/SHA; независимо извлечь текст штатным
`C:/Program Files/Git/mingw64/bin/pdftotext.exe`; визуально сверить ур.(17), Table1, график/формальную область
с -17. До такого чтения содержание -18 и необходимость изменений формул/домена остаются OPEN.

## Дополнительная проверка R29: Python/OpenSSL

Мини-intent agora #2809, результат #2812. Git curl 8.17.0 оказался тоже Schannel (проверена только версия;
повторной загрузки им не было). В установленном Python `ssl.OPENSSL_VERSION` — `OpenSSL 3.0.18 30 Sep 2025`.

Выполнен один вызов stdlib `urllib.request.urlopen` для загрузки того же официального PDF с
`ssl.create_default_context()`. `check_hostname=True`, `verify_mode=CERT_REQUIRED`; проверка сертификата
не отключалась. Таймаут сокета 15 с, проверка общего времени 30 с между чтениями, предел 32 MiB.
Уникальные временная папка и файл создавались бы только после получения ответа. Проверки полного файла
были предусмотрены: `%PDF-`, маркер EOF, Content-Length, размер и SHA-256.

Фактический результат: exit 1 через 0.177 с, **до HTTP-ответа**:

```text
URLError: <urlopen error [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol (_ssl.c:1081)>
```

Статус/заголовки HTTP не получены; временная папка, partial и PDF не создавались. Повторов не выполнялось.
Наблюдалось завершение TLS-соединения с указанным кодом; первопричина не установлена. Политика сервера
не исследована. Содержимое P.372-18 остаётся OPEN, Core/REQ/формулы не менялись.

Минимальное воспроизведение именно TLS-этапа (при успехе выводит статус, файл не сохраняет):

```powershell
@'
import ssl, urllib.request
context = ssl.create_default_context()
assert context.check_hostname and context.verify_mode == ssl.CERT_REQUIRED
with urllib.request.urlopen('https://www.itu.int/dms_pubrec/itu-r/rec/p/R-REC-P.372-18-202609-I!!PDF-E.pdf', context=context, timeout=15) as response:
    print(response.status)
'@ | python -B -I -
```
