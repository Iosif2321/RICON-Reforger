## Прямые наблюдения

Все строки таблицы сохраняются в 28 общих срезах каждой стороны.

| Сторона и наблюдаемый ID | Контроллер | Сущность через PlayerManager | Сущность через контроллер | Respawn игрока |
|---|---:|---:|---:|---|
| Хост → 1 | 1 | 1 | 1, та же ссылка | 1 |
| Хост → 2 | 1 | 0 | 0 | 1 |
| Клиент → 2 | 1 | 0 | 0 | 1 |
| Клиент → 1 | 0 | 0 | 0 | UNKNOWN: чужая область API |

На обеих сторонах у GameMode есть RespawnSystemComponent, но
`respawnEnabled=0`. Объект логики есть, его фактический класс — `SCR_SpawnLogic`.
`SCR_SpawnPoint.CountSpawnPoints()` возвращает 0. FactionManager и LoadoutManager
присутствуют. Это совместимые показания: наличие компонента не означает,
что появление разрешено или реализовано нужным вариантом логики.

Нулевое назначение игрока 1 на клиенте **не доказывает отсутствие реплики
персонажа**: здесь проверяется доступное назначение через PlayerManager.
Отсутствие чужого контроллера также не принимается за разрыв соединения.
Ограничение respawn API подтверждено
[официальной документацией PlayerManager](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfacePlayerManager.html).

## Что следует из опыта

Сетевое соединение работоспособно, а второй игрок остаётся без назначенного
персонажа. Тестовый Plain с отключённым появлением, базовой логикой и нулём
точек не готов к проверке радио у двух персонажей. Это ограничение стенда,
а не установленная неисправность ядра RICON или VoN.

Причинная гипотеза: хостовый персонаж появляется по специальному пути Workbench
Play from camera, а полноценный путь появления удалённого игрока в Plain
не настроен. Согласуется с наблюдениями и операторским разбором строк создания,
но точный путь установленной версии ещё нужно прочитать. Публичная API
[SCR_SpawnLogic](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfaceSCR__SpawnLogic.html)
разделяет HandlePlayFromCamera и реализации DoSpawn_S в Auto/Menu-вариантах;
текущая веб-документация сама по себе не доказывает реализацию установленной версии.

Следующий шаг: прочитать минимальные участки установленной логики появления,
выбрать штатный способ для отдельного TOOL_ONLY стенда и согласовать с Claude
точный план. Один вызов включения respawn не считается достаточным исправлением.
Приёмка следующего опыта потребует ненулевого назначения игрока 2 на сервере
и собственном клиенте, затем наличия рации/VoN; слышимость проверяется отдельно.

## Уточнение по установленным исходникам

После B0d выполнены пять коротких чтений через ScriptEditor, без мира и Play.
[Квитанция с SHA и диапазонами](receipts/b0e-spawn-source-codex.json).
В репозиторий перенесены факты, исходники игры не копировались.

- `SCR_SpawnLogic.c:532–534`: тело базового DoSpawn_S пустое. Поэтому включение
  respawn при сохранении именно этого класса не добавляет реализацию этого шага.
- `SCR_AutoSpawnLogic.c:38–60`: выбирается заданная либо случайная фракция,
  запрашиваются фракция и подходящая экипировка; отсутствие назначенной фракции
  завершает попытку через обработчик неудачи.
- `:62–74`: отсутствие назначенной экипировки или точки появления своей фракции
  также завершает попытку. Простого существования любого spawn point недостаточно.
- `:76–83`: данные содержат ресурс экипировки и RplId точки; после проверки
  CanSpawn выполняется штатный RequestSpawn.
- `:31–34`: после ошибки предусмотрена отложенная повторная попытка. Это не
  основание оставлять неполный стенд бесконечно работающим.

Эти факты подтверждают выбор штатной авто-логики для следующего стенда, но не
доказывают её успешный запуск с ещё не созданной конфигурацией мира.

Поиск штатных префабов `183706` нашёл AutoSpawn уже в
`Prefabs/MP/Modes/Plain/GameMode_Plain.et:9–12` и
`Prefabs/MP/Modes/Deathmatch/GameMode_Deathmatch_Base.et:4–7`.
Следовательно, базовый класс в runtime B0d нельзя автоматически приписать
неизменённому префабу Plain: остаются переопределение экземпляра мира и
изменение при инициализации. Попытка текстового чтения Autotest-мира `183807`
завершилась INCOMPLETE (ресурс найден, файл не открыт), не отрицательным результатом.
Следующий метод — прочитать компонент экземпляра и его предка через редактор.

## Готовый кандидат MpTest

Субагент codex `world_route` выполнил отдельную проверку только чтением:
установленный SDK `interfaceSCR__AutotestHelper.html:131` содержит
WORLD_MPTEST с ResourceName `{96A8AF57260A7392}worlds/MP/MpTest/MpTest.ent`.
Официальное [General Game Mode Setup](https://community.bistudio.com/wiki/Arma_Reforger%3AGeneral_Game_Mode_Setup)
описывает MpTest как Plain, автоматическое появление и FFA.

Ограниченный текстовый поиск `rg -a -o` по установленному
`Arma Reforger/addons/data/resourceDatabase.rdb` отдельно нашёл MpTest.ent,
MpTest_Basic.ent, MpTest_Empty.ent и Missions/MpTest/10_MpTest.conf.
Размер RDB — 11 509 935 байт, SHA256
`c5344847875ab4c94cf3cda88c5f9cc60878b799f33b2137c8e4a18726c19b7c`.
Распаковка .pak и чтение самого мира не выполнялись.

Поэтому готовый MpTest проверяется перед созданием нового мира. Известный
отрицательный результат MpTest_Empty не относится ко всем вариантам MpTest.
Inventory не заменяет WorldList и опыт назначения персонажа.
