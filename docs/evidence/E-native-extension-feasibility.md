README отдельно ограничивает опубликованный механизм dedicated server/Workbench, не игровыми клиентами.
Слово client в «host/client DLL» обозначает плагин относительно host; оно не доказывает поддержку игрового клиента.
Лицензия опубликованного SDK — APL-SA; из неё нельзя выводить разрешение автора движка на любой способ расширения.
Этот документ не выносит общего юридического заключения и не утверждает неизбежность блокировки античитом.

## Конкретный следующий опыт

1. Сначала подобрать host с подтверждённой поддержкой установленной сборки и совместимым SDK. Текущее состояние
   **HOST_COMPATIBILITY_UNVERIFIED**; запуск Alpha8 на 1.8.0.13 не заменяет эту проверку.
2. В отдельном TOOL_ONLY проекте проверить одну собственную `proto`-функцию с известным числовым результатом,
   загрузку класса и версию ABI. Нужны положительный контроль и отсутствие host: отсутствие отмечается явно,
   без вызова незагруженной proto-функции. Такой опыт проверяет мост, не управление голосом.
3. Затем через проверенную reflection-поверхность получить имена доступных типов `BaseTransceiver`,
   `VoNComponent`, `RadioManagerEntity`; отсутствующие типы и незавершённые методы отмечать отдельно.
   Наличие типа не доказывает доступ к его приватному аудиопотоку или право менять получателей.
4. К вмешательству переходить только с конкретной точкой API/хуком. Проверка: блок A→B на выбранной радиопаре,
   A→C/C→B/B→A и второй радиопуть A→B сохранены, native DIRECT неизменен. На одном канале контрольные передачи
   последовательны. Само исчезновение `OnReceive` без наблюдаемого клиента не считается тишиной.

Точки штатного script-наблюдения и прибор разрабатываются параллельно (`E-von-windows-ea.md`,
`tools/RICON_LiveProbe`); они не требуют этой DLL. Итог G-DLL: способ добавлять C++ функциональность найден,
но полный контроль клиентского радио и работоспособность выбранного host в текущей сборке ещё не проверены.
