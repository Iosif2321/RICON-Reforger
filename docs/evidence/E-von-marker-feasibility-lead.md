# Тестовая информация вместо звука: проверка осуществимости

Дата: 2026-11-02. Уровень: **DOC + WORKBENCH_SOURCE, не передача данных**. Вход: `249507a`, подтверждение и поправка владельца в событии 680 рабочего Thread. Исходные страницы/журналы и SHA-256 — в [квитанции](<receipts/von-marker-feasibility-20261102-lead.json>).

**Итог:** найден штатный кандидат для следующего минимального опыта — `VoNComponent.SoundEventPriority`. Валидного пакетного заменителя голоса пока не доказано. Обычное радиосообщение и временной рисунок RX нельзя автоматически объявлять тем же VoN-протоколом.

## 1. Обычное радиосообщение: недостаточно общего трансивера

`BaseTransceiver.BeginTransmission(BaseRadioMessage)` и `ScriptedRadioMessage.OnDelivery(receiver, freq, quality)` существуют. У `VonRadioMessage` публичная страница не показывает собственный payload API; открытая сериализация произвольных байтов в изученных членах не описана.

Для конкретного ванильного `SCR_CampaignRadioMsg` прослежено: OnDelivery выбирает владельца/PlayerController, получает `SCR_CampaignNetworkComponent` и вызывает `PlayRadioMsg`. Последний явно вызывает `Rpc(RpcDo_PlayRadioMsg, ...)` — отдельную передачу данных кампании. Это **не** доказательство player-voice media-пути. Вывод относится к прочитанной реализации, не является доказательством невозможности всех иных scripted radio messages.

## 2. Предпочтительный кандидат: AI sound event через VoN

Установленный API прямо описывает `VoNComponent.SoundEventPriority(string eventname, array<float> values, int priority, bool ignoreQueue=false)` как «Transfer AI sound message through VoN». Вызов принимает событие и параметры, а не PCM-буфер; это основание проверять его раньше обходов микрофонного ввода, но не доказательство уже работающей передачи между player-role.

Отдельно существует `CommunicationSoundComponent.SoundEventPriority(string eventName, int priority, bool ignoreQueue=false)`: это очередь звуковых событий. Одно имя методов **не доказывает связь двух overload**. Общий поиск Workbench показал вызовы именно communication-варианта; срез был ограничен 15 строками и не является исчерпывающим поиском VoN callsites.

У `SCR_CommunicationSoundComponent` подтверждён `GetOnSoundEventStarted`; исходный override передаёт в invoker component/eventName/AudioHandle/priority. Это кандидат приёмного observable. Но callback сам по себе — событие воспроизведения, не удостоверенная удалённая VoN-доставка. В прочитанном SCR-файле поиск VoN дал 0 совпадений; поведение native-родителя этим не установлено. Получение на B массива `values`, радиоветвь, serializer и прохождение через тот же mute-stage остаются UNKNOWN.

Минимальное опровержение для следующей спецификации: B не получает тестовое содержимое обходным способом; на A выбирается свежая неизвестная B последовательность допустимых событий/маркеров; B сохраняет только реально наблюдённые данные и результат до раскрытия A. Нужно одновременно подтвердить native radio/VoN binding и действие реальных ограничений тракта. Если виден лишь локальный callback, другая репликация либо радио-gate не влияет на этот поток — такой заменитель не принят. Числа/nonce нельзя просто положить в общий конфиг или RPC B.

## 3. Временной маркер на настоящих RX: более слабый кандидат

Можно проектировать декодер, восстанавливающий скрытый nonce по наличию native radio OnReceive в заранее откалиброванных временных слотах. B использует только свои часы и конкретный неизменный RX handle, sender A и local B; никакого расписания/seed/логов A на B. Все попытки, gaps и отказы сохраняются; калибровка отделена от тестового nonce.

Но API не обещает пакетную каденцию, frame id, payload, отсутствие VAD или отправку при тишине. Поэтому это максимум кандидат `VON_RX_TIMING_MARKER`. Реальные capture/PTT и audio-for-playback RX должны быть наблюдены отдельно. Нельзя подставить local PTT вместо отсутствующего RX. CRC подтверждает целостность, не источник и не протокол.

Особенно важно: mute может действовать **после** OnReceive. Тогда декодированный временной маркер продолжит приходить при подавленном воспроизведении и не докажет участие H2 или сохранность direct. Отключать декодер локальным флагом для «подтверждения» запрета запрещено. Без разграничения media/control пути эквивалентность остаётся UNKNOWN.

## 4. Что действительно выполнено

Только чтение установленного API и существующего WbReader через ScriptEditor: без мира, Play, сервера, SetCapture, передачи маркеров, аудиозаписи и UI-нажатий. Все читающие процессы завершены; исходники инструмента и production не изменялись. Первый поиск с неверным resource root завершился SearchResources=false/exit 3 и не считается отрицательным ответом по API. Повтор по всей ResourceDatabase и адресные окна дали успешное завершение reader; каждое окно не превышало 15 строк.

## 5. Передача дальше

[INTENT v0.2](<../req/INTENT-local-radio-slice.md>) записывает подтверждение владельца и допускает информацию вместо звука. Для следующей **новой сессии проектирования** рекомендуемым первым кандидатом является AI-event вход VoN с независимо квалифицированным приёмом на B. Требуется DRAFT спецификации опровергающего probe, а не сразу runtime-PASS или production-актуатор. Если выбран временной канал, его более слабая доказательность должна оставаться в имени результата и матрице критериев.

`SAME_PATH_PACKET_PASS`, слышимость, действие RICON и полный AUDIO_PASS по этой проверке не получены.
