# B0c: первый отдельный клиент и отказ по дубликату личности

Дата: 2026-10-25. Codex — независимая проверка, claude — оператор.
Запуск: `ricon-b0c-serverplay-claude-20261025-202016`.
Код наблюдателя: 3f2ce83; оператор: fae6532.

## Первый опыт 202016

**B0c не пройден:** устойчивого второго игрока нет. Хост корректно завершил
свою часть опыта, но это не является успешным подключением клиента.

Codex независимо прочитал raw console.log хоста и сверил SHA
`f789a82961f7095e0503ecaa078b0f398a38bf23e742b2e242ce97041c2574b8`:

- 125 событий в потоке, 120 срезов, SCRIPT(E)=0;
- во всех срезах members=1;
- сервер получил запрос подключения, отправил мир и подтверждение валидации;
- затем сопоставил новое соединение с уже подключённым игроком и отключил
  его с кодом `0x00060002`; число игроков осталось равным одному.

По [квитанции оператора](receipts/b0c-client-claude-20261025.txt), коммит 825e4e5:

- клиент действительно запущен как отдельный Diag-процесс, роль Client (1);
- после рукопожатия, загрузки мира и валидации он получил PlayerId=1,
  затем был отключён как дубликат личности;
- наблюдатель клиента завершился через GAME_END без срезов;
- при последующей выгрузке мира появилось окно assertion о ресурсах
  (`GameApp.cpp:1287`); кнопки окна не нажимались;
- хост восстановил исходные настройки, клиент и WB завершены; регистрируемые
  изменения реестра и профиля отсутствуют.

SHA клиента по квитанции —
`2f46010d3759994acccde20a7706a058f47601cffe0ad1df65c2db2a6c33a307`;
SHA crash.log — `581be1f3f4fdc87e6ed6600ef76884955c8c1862cde902802485884ed6f5214b`.
Эти два файла в этом шаге codex напрямую не перечитывал. Настоящее имя
пользователя и адрес подключения в документ не включены.

## Подтверждённый кандидат для следующего опыта

В установленной официальной документации SDK
`Workbench/docs/EnfusionScriptAPI/html/Page_CLI.html:321`, раздел Platform
Service, найден параметр `-username`. Описание прямо указывает его назначение:
переопределение имени в platform service для нескольких локальных клиентов
на одном сервере при разработке. Видимость параметра обозначена ENF_DEVELOPER.
SHA файла документации:
`b1fd25c1d02e3ac687bb310496f700acaf451f66d26c572afa9ac5fd343822d1`.

Следующий кандидат — добавить **только клиенту**
`-username RICON_B0c_peer1`, сохранив остальные параметры и отдельный временный
профиль. Это штатный тестовый механизм по документации; применение аргумента
именно нашим Diag-бинарником ещё не подтверждено. Успех потребует нового
отличающегося PlayerId и его одновременного присутствия в срезах хоста.
Имя аккаунта Steam, серверная проверка личности и проверки совместимости
не изменяются. Assertion не обходится нажатием «Пропустить».

2026-10-26 выполнено дополнительное чтение PeerTool через Workbench:
`ricon-wbreader-codex-peer-identity95-20261026-132804`, SHA
`c7a3adf0ea4110c511f790151ead07e834a74fc75599cdc0b792955ed4a642d8`.
Прочитаны строки 95–109 через ScriptEditor, без мира и Play. Reader завершился,
exit=0, SCRIPT(E)=0; при завершении движок напечатал Resource leaks, поэтому
отсутствие всех ошибок движка не заявляется.

Пропущенные ранее строки 95–98 добавляют forceupdate и nofocus. В просмотренной
сборке команды 65–122 отдельное имя автоматически не добавляется; Params
передаётся в команду непосредственно. Это подтверждает возможность передать
параметр через Params, но не доказывает, что стандартная конфигурация PeerTool
уже задаёт username. Основанием для выбора аргумента остаётся документация SDK;
следующий живой опыт должен проверить фактическое отдельное имя клиента.

## Отдельное имя применилось: 144401

В повторе 2026-10-26 с `-username RICON_B0c_peer1` хост создал PlayerId=2
для этого имени, без сообщения о дубликате. Codex независимо сверил raw SHA
`cc93c13206d701d61c241787ed40717af37725fc30d49a4e572f0a6b0362efea`.
На хосте записаны 14 событий, включая 10 срезов; последний seq=13 не является
числом срезов. Второе окно ванильного запроса :1101 остановило операторский
скрипт. Поэтому новое имя подтверждено, а устойчивое соединение этим опытом
ещё не принималось.

После отдельного разрешения владельца (#4972) guard dd6f5cb допускает второй
точный Yes только в клиентском опыте, после создания тестового PlayerId=2,
в прежней разрешённой фазе. Общий предел — два, Yes to All не используется.
Codex выполнил 10 независимых проверок regex и квоты без UI; авторские проверки
окна и счётчика — 2 × 343/343 у claude.

завершены, реестр и профиль без изменений. Это UI/OS-измерения claude, а не
отдельный графический прогон codex.

**B0c подтверждён в объёме соединения двух участников.** У клиента pc=1,
controlled=0, vonEntries=0; его RADIO_STATE в журнале отсутствует. Причина
отсутствия управляемой сущности этим наблюдением не установлена. Следующий
этап должен различить отсутствие сущности на сервере, отсутствие назначения
контроллеру и отсутствие её представления у клиента. Слышимый голос и
точечное подавление A→B остаются непроверенными.
